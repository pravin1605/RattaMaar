Q. How can you improve SQL query performance?? //(How would you optimize a slow SQL query?) IMP

1. Use Proper Indexes

  • Indexes make data retrieval faster (like a book's index).
  • Example: If you frequently search by employee_id, put an index on that column.
▲ But don't create too many indexes, they slow down inserts/updates.

2. Avoid SELECT *

  • Instead of fetching all columns, only select what you need.
✗ SELECT * FROM employees; ✅ SELECT name, salary FROM employees;

3. Use Joins Wisely

  • Prefer INNER JOIN over OUTER JOIN if you don't need all data.
  • Ensure join columns are indexed.

4. Filter Early (WHERE instead of HAVING)

  • Use WHERE to filter rows before grouping/aggregating.
  • Example:
✗ SELECT dept, COUNT(*) FROM employees GROUP BY dept HAVING salary > 50000; ✅ SELECT dept, COUNT(*) FROM employees WHERE salary > 50000 GROUP BY dept;

5. Use LIMIT or TOP for Large Tables

  • If you need only a few rows, don't scan the whole table.
✅ SELECT name FROM employees ORDER BY salary DESC LIMIT 5;

6. Avoid Subqueries if Possible (Use Joins/CTEs)

  • Subqueries can be slow.
✗ SELECT * FROM employees WHERE dept_id IN (SELECT id FROM departments); ✅ Use JOIN: SELECT e.* FROM employees e JOIN departments d ON e.dept_id = d.id;

7. Analyze Execution Plan

  • Use EXPLAIN (MySQL/Postgres) or EXPLAIN PLAN (Oracle/SQL Server) to see how SQL runs your query.
  • This shows if indexes are used or full table scans are happening.

8. Partition Large Tables

  • Split very large tables (millions of rows) into smaller parts for faster access.

9. Use Proper Data Types

  • Choose correct column types (INT vs VARCHAR).
  • Example: Storing numbers in VARCHAR slows comparisons.

10. Cache Frequently Used Queries

  • If the same query runs often, cache results instead of hitting the database every time.

Simple Example:

Suppose this query is slow:

SELECT * FROM employees WHERE department = 'IT' AND salary > 60000;

✅ Optimization Steps:

  1. Add an index on department and salary.
  2. Remove SELECT * → SELECT name, salary.
  3. Check execution plan.

Q57. What is the CASE statement in SQL?

The CASE statement in SQL is like an IF-ELSE ladder.
It lets you check conditions and return different values depending on which condition is true.

☑ Syntax

CASE WHEN condition1 THEN result1 WHEN condition2 THEN result2 ... ELSE resultN END

Real-Life Example: Student Grade

Like a teacher giving grades: 90+ marks = A, 75+ = B, otherwise = C.

SELECT name, marks, CASE WHEN marks >= 90 THEN 'A' WHEN marks >= 75 THEN 'B' ELSE 'C' END AS grade FROM students;
  • SQL checks conditions top to bottom and stops at the first one that is true.

⑰ What are the limitation of Views

A View is a saved SELECT query. It does not store data itself (a normal view), it only shows data from tables.

  • Performance: runs the query every time you use it. A complex view on big tables is slow.
  • Limited DML: INSERT/UPDATE/DELETE often not allowed if the view has JOIN, GROUP BY, DISTINCT, or aggregate functions.
  • No parameters: a view cannot take input values (a stored procedure or function can).
  • Depends on base tables: if a table or column is dropped or renamed, the view breaks.
  • ORDER BY is not allowed in a view in SQL Server (unless TOP is used).
  • Indexes: cannot normally index a view (only materialized / indexed views can).
  • Nested views (view on view) are hard to debug and slow.

Real-life example: A view is like a window into a room. You can see what's inside, but you can't rearrange the furniture through it, and if the room is demolished (table dropped), the window shows nothing.

⑱ Explain what is Nolock

  • Nolock allows you to read data without waiting For locks to be released
  • Faster reading
  • Avoids waiting / blocking
SELECT * FROM orders WITH (NOLOCK);
▲ Risk: Dirty Read. You may read data that is not yet committed and later rolled back.

Real-life example: A shopkeeper is updating the price tag on a product. With NOLOCK you take a quick look and read the old/half-updated price instead of waiting. Fast, but the price may be wrong.

  • Use for reports where exact accuracy is not critical. Not for money/banking data.

⑲ Types of Locks

① Shared lock (Read lock)

  • Multiple users can read the data
  • No one can modify the data while the shared lock exists

Real-life example: Many people reading the same notice board at once. All can read, but nobody can change the notice while people are reading.

② Exclusive lock (Write lock)

  • Applied when a user performs Insert, update or Delete
  • other users cannot modify the same data until commit or rollback

Real-life example: One person is in a changing room. Door is locked, and nobody else can enter until they come out.

Problems explained with examples

  • Dirty read: You read a bank balance that someone just changed but has not committed. They roll back, and the number you saw never existed.
  • Non-repeatable read: You check a product price = ₹100, check again in the same transaction and it is ₹120 because someone updated it.
  • Phantom read: You count 10 orders, count again and now there are 11 because someone inserted a new row.

Real-life example: Four levels of privacy in an exam hall, from "everyone can peek at your paper" (Read Uncommitted) to "each student sits in a separate room" (Serializable). More privacy = safer but slower.

Interview tip: Higher isolation = more safety but less speed. Most systems use Read Committed.
