Functional Dependency

A Functional Dependency (FD) exists when the value of one attribute uniquely determines the value of another attribute in a table.

In simple words: if you know column A and that is enough to find column B, then B is functionally dependent on A.

Notation   A → B
Read as   A determines B

Left side (A) is called the Determinant. Right side (B) is called the Dependent.

Quick revision: words you must know

  • Attribute = a column (Name, Dept)
  • Tuple = a row (one student's full record)
  • Super Key = any column set that identifies a row uniquely (RollNo, or RollNo+Name)
  • Candidate Key = the smallest super key (nothing can be removed from it)
  • Primary Key = the candidate key we choose as the main one
  • Composite Key = a key made of 2 or more columns, e.g. (RollNo, Subject)
  • Prime attribute = a column that is part of some candidate key
  • Non-prime attribute = a column that is NOT part of any candidate key

Real life examples (easy to remember)

  • Aadhaar number → Person name, DOB : one Aadhaar number belongs to only one person.
  • PIN code → City : PIN 400001 always means Mumbai.
  • Vehicle number → Owner : one plate number, one registered owner.
  • Name → Phone is NOT an FD, because two people can have the same name with different phones.

Trick to test an FD: find two rows with the same A value. If their B values are different, then A → B is false.

Trivial and Non-trivial FD

  • Trivial FD : B is already part of A. Example: (RollNo, Name) → Name. It is always true, so we ignore it.
  • Non-trivial FD : B is not part of A. Example: RollNo → Name. These are the ones we study.

Types of Functional dependency

  1. Total Functional dependency
  2. Partial Functional dependency
  3. Transitive Functional dependency

① Total Functional dependency

  • If one attribute (or key) in a relation determines all the other attributes, it is known as TFD.
  • If all the attributes are dependent on a single attribute, it is also known as TFD.
  • Also, if the key has many columns, the dependent attribute needs the whole key, not just a part. Example: (RollNo, Subject) → Marks.
EMP( EID, EName, SAL, DOB) EID → EName EID → SAL EID → DOB EID → (EName, SAL, DOB)

Here EID is the key, so it determines everything. This is the healthy situation we want in every table.

② Partial Dependency

A Partial Dependency occurs when a non-key attribute depends on only part of a composite primary key, instead of the whole key.

This problem appears only when the primary key has more than one column. (If the key is a single column, partial dependency is not possible.)

Problem: Pravin's name is stored again for every subject. Wasted space, and risk of typing "Pravin" in one row and "Pravn" in another.

Real life example of Partial Dependency

Online shopping table OrderItem(OrderID, ProductID, ProductName, Qty) with key (OrderID, ProductID).

  • (OrderID, ProductID) → Qty   ✔ needs the whole key
  • ProductID → ProductName   ✘ needs only part of the key (partial)

If 1000 orders contain "Wireless Mouse", the name is repeated 1000 times.

③ Transitive Dependency

A Transitive Dependency occurs when a non-key attribute depends on another non-key attribute, which in turn depends on the primary key.

In simple words, the dependency goes through another column (like a middle man).

Normalization

  • It is the process of reducing a large table in order to remove redundancy and anomalies by identifying their functional dependencies.
  • The process of decomposing (breaking) a large table into smaller tables is known as Normalization.
  • Reducing a table to its Normal Form is known as Normalization.

Why do we need Normalization?

A badly designed table has redundancy (same data stored again and again). Redundancy causes anomalies (bugs in data). Example food-order table:

orders (bad design)
OrderIDCustomerCityItemPrice
1RaviMumbaiPizza250
2RaviMumbaiBurger120
3SnehaPunePizza250

Three anomalies

  1. Insertion anomaly : you cannot add a new customer (say Amit) until he places an order, because OrderID would be empty.
  2. Update anomaly : Ravi shifts to Delhi. You must change City in every row. If you miss one row, the data becomes inconsistent (Mumbai and Delhi both).
  3. Deletion anomaly : if you delete Order 3, you also lose all information about Sneha and that she lives in Pune.

Fix: keep Customer data in one table, Order data in another. That is Normalization.

What is Normal form

  • A table without redundancy and anomalies is said to be in Normal Form.

Levels of Normal Form

  1. First Normal Form (1NF)
  2. Second Normal form (2NF)
  3. Third Normal form (3NF)
  4. Boyce-Codd Normal Form (BCNF)

Each level includes the previous one. A table in 3NF is already in 2NF and 1NF.

If any table / entity is reduced to 3NF, then the table is said to be Normalized.

First Normal Form (1NF)

A table is in 1NF if every cell holds only ONE value (atomic value), there are no repeating groups, and each row is unique.

Rules of 1NF

  • Each cell has a single value (no lists like "Math, Sci").
  • No repeating columns (Phone1, Phone2, Phone3).
  • Each column has the same type of data.
  • Each row is unique (a primary key exists).

Example (before 1NF)

student (NOT in 1NF)

Problem: Pravin has two phones in one cell. How will you search or update just one number?

Now the key becomes (RollNo, Phone). Name is repeated, which will be fixed in 2NF.

Real life example

Online order table with column Items = "Pen, Book, Bag". Not 1NF. Make one row per item: (OrderID, Item).

Second Normal Form (2NF)

A table is in 2NF if it is in 1NF and has NO partial dependency (every non-key attribute depends on the whole primary key).
  • 2NF only matters when the primary key is composite.
  • If the primary key is a single column and the table is in 1NF, it is automatically in 2NF.

Steps to convert into 2NF

  1. Find the primary key (composite).
  2. Find attributes that depend on only a part of the key.
  3. Move them to a new table together with that part of the key.
  4. Keep the rest in the old table.

Example

student_marks(RollNo, Sub, Name, Marks), key (RollNo, Sub). Here RollNo → Name is partial. Split it:

Now Pravin's name is stored only once. In marks table, Marks depends on the full key (RollNo, Sub). ✔

Real life example

OrderItem(OrderID, ProductID, ProductName, Qty) becomes:

  • Product(ProductID, ProductName)
  • OrderItem(OrderID, ProductID, Qty)

Now a product name can be changed in one place only.

Third Normal Form (3NF)

A table is in 3NF if it is in 2NF and has NO transitive dependency (no non-key attribute depends on another non-key attribute).

Easy line to remember: "Every non-key attribute must depend on the key, the whole key, and nothing but the key."

Steps to convert into 3NF

  1. Find chains like A → B → C where A is the key.
  2. Make a new table with B and C (B becomes its primary key).
  3. In the old table keep A and B (B stays as foreign key), remove C.

Example

student(RollNo, DeptID, DeptName) has RollNo → DeptID → DeptName. Split it:

If the department name changes from "Extc" to "EXTC Engg", you update only one row.

Real life example

Employee(EmpID, Pincode, City) becomes Employee(EmpID, Pincode) and PinMaster(Pincode, City).

The same thing in SQL

CREATE TABLE department ( DeptID VARCHAR(5) PRIMARY KEY, DeptName VARCHAR(30) ); CREATE TABLE student ( RollNo INT PRIMARY KEY, DeptID VARCHAR(5), FOREIGN KEY (DeptID) REFERENCES department(DeptID) ); -- get DeptName back using JOIN SELECT s.RollNo, d.DeptName FROM student s JOIN department d ON s.DeptID = d.DeptID;

Boyce-Codd Normal Form (BCNF)

A table is in BCNF if for every non-trivial FD X → Y, X is a Super Key.

BCNF is a slightly stronger version of 3NF. It fixes the rare case where a non-key column determines a part of a key.

Example

class(Student, Subject, Teacher). Rules: each teacher teaches only one subject; a student has one teacher per subject.

StudentSubjectTeacher
RaviDBMSMehta
SnehaDBMSMehta
RaviOSJoshi
  • Keys: (Student, Subject) and (Student, Teacher)
  • FDs: (Student, Subject) → Teacher, and Teacher → Subject
  • Teacher is not a super key, so Teacher → Subject breaks BCNF.

Fix: split into teacher_subject(Teacher, Subject) and student_teacher(Student, Teacher).

All Normal Forms in one table

FormConditionRemoves
1NFAtomic values, no repeating groupsMulti-valued cells
2NF1NF + no partial dependencyPart-of-key dependency
3NF2NF + no transitive dependencyNon-key → non-key
BCNFEvery determinant is a super keyRemaining FD problems

Good decomposition rules

  • Lossless join : after splitting, a JOIN must give back exactly the original data (no missing rows, no fake rows).
  • Dependency preserving : all original FDs should still be checkable in the new tables.
  • Use a common column (PK-FK) to connect the split tables.

Advantages and Disadvantages

  • Advantages : less redundancy, no anomalies, less storage, easy updates, better data consistency.
  • Disadvantage : more tables means more JOINs, so some read queries become slower.
  • That is why big reporting systems sometimes do Denormalization (joining tables on purpose for speed).
Exam tip: 1NF → atomic cells. 2NF → remove partial. 3NF → remove transitive. BCNF → every determinant must be a super key.

Extra Theory: Rules to Work with FDs

Armstrong's Axioms (basic rules)

  1. Reflexivity : if B is part of A, then A → B. Example: (RollNo, Name) → Name.
  2. Augmentation : if A → B, then AC → BC. Example: RollNo → Name, so (RollNo, Sub) → (Name, Sub).
  3. Transitivity : if A → B and B → C, then A → C. Example: RollNo → DeptID and DeptID → DeptName, so RollNo → DeptName.

Extra rules made from these three:

  • Union : A → B and A → C gives A → BC.
  • Decomposition : A → BC gives A → B and A → C.

Attribute Closure (A⁺)

The closure of A (written A⁺) is the set of ALL attributes that can be found starting from A using the given FDs.

Use: if A⁺ contains every column of the table, then A is a Super Key. If no smaller part of A works, A is a Candidate Key.

Steps

  1. Start with result = A.
  2. Look for an FD whose left side is already inside the result. Add its right side.
  3. Repeat until nothing new is added.

Example

Table student(RollNo, Name, DeptID, DeptName) with FDs: RollNo → Name, RollNo → DeptID, DeptID → DeptName

finding the closure of RollNo
StepFD usedResult so far
Start-{RollNo}
1RollNo → Name{RollNo, Name}
2RollNo → DeptID{RollNo, Name, DeptID}
3DeptID → DeptName{RollNo, Name, DeptID, DeptName}

RollNo⁺ has all 4 columns, so RollNo is the candidate key. But DeptID⁺ = {DeptID, DeptName} only, so DeptID is not a key. This is exactly why DeptID → DeptName is a problem (transitive).

How to find the highest Normal Form of a table

  1. Find all candidate keys using closure.
  2. Any multi-valued cells? If yes, it is not even 1NF.
  3. Any non-prime column depending on part of a candidate key? If yes, it is only 1NF.
  4. Any non-prime column depending on another non-prime column? If yes, it is only 2NF.
  5. Any FD X → Y where X is not a super key? If yes, it is only 3NF. If no, it is BCNF.

  • Insert anomaly : to add a new department D40 (Mech) with no students yet, we need a RollNo and Sub, which do not exist.

Extra theory: 1NF

  • 1NF is violated by 3 things: multi-valued cells (many subjects in one cell), repeating columns (Sub1, Sub2, Sub3) and composite cells like Address = "Andheri, Mumbai, 400053" (split it into Area, City, Pincode).
  • "Atomic" means the smallest piece you will ever search or update separately.
  • 1NF is the base rule of the relational model. In SQL, every table should be at least 1NF.
  • 1NF fixes the structure, but it does not remove redundancy. That is the job of 2NF and 3NF.

Extra theory: 2NF

  • Formal idea: no non-prime attribute should depend on a proper subset of a candidate key.
  • If every candidate key is a single column, the table is automatically in 2NF.
  • The split must be lossless: RollNo is kept in both tables, so a JOIN on RollNo rebuilds the 1NF table exactly.

Extra theory: 3NF

  • Formal rule: for every FD X → A, either X is a super key, or A is a prime attribute (part of a candidate key).
  • 3NF is the normal form most real projects stop at, because it removes most redundancy and keeps all FDs checkable.
  • 3NF vs BCNF: they differ only when a table has overlapping candidate keys, like the Student-Subject-Teacher example. Otherwise 3NF = BCNF.

Getting the old data back with JOIN

SELECT s.RollNo, s.Name, d.DeptName, m.Sub, m.Marks FROM student s JOIN department d ON s.DeptID = d.DeptID JOIN marks m ON s.RollNo = m.RollNo;

This gives the same 6 rows as the 1NF table, so no information was lost.
