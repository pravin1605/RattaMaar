1. Entity Class — Person.java

ORIGINAL CODE 
package com.ty;

import javax.persistence.Entity;
import javax.persistence.Id;

/*
 * @Entity
 * Marks this class as Hibernate Entity Class.
 * Hibernate maps this class with a database table.
 */
@Entity
public class Person {

	/*
	 * @Id
	 * Marks p_id as Primary Key.
	 */
	@Id
	private int p_id;

	private String pName;
	private int pAge;

	// Default Constructor (Recommended)
	public Person() {

	}

	// Getter and Setter Methods

	public int getP_id() {
		return p_id;
	}

	public void setP_id(int p_id) {
		this.p_id = p_id;
	}

	public String getpName() {
		return pName;
	}

	public void setpName(String pName) {
		this.pName = pName;
	}

	public int getpAge() {
		return pAge;
	}

	public void setpAge(int pAge) {
		this.pAge = pAge;
	}
}
EXTRA — Explanation
  • @Entity tells Hibernate/JPA that this POJO maps to a database table. By default the table name = class name (Person), unless overridden with @Table(name="...").
  • @Id marks the primary key field. Every entity must have exactly one field annotated @Id.
  • A no-arg (default) constructor is mandatory for JPA — Hibernate uses reflection to instantiate entities, and it requires this constructor even if you never call it yourself.
  • Fields without explicit @Column are auto-mapped to columns with the same name as the field (pName → column pName). You can rename columns with @Column(name="p_name").
  • Because there's no @GeneratedValue on p_id, the ID is assigned manually by the application (as seen in PersonDriver: p.setP_id(1)) rather than auto-generated by the database.

2. Insert — PersonDriver.java (persist())

ORIGINAL CODE 
package com.ty;

import javax.persistence.EntityManager;
import javax.persistence.EntityManagerFactory;
import javax.persistence.EntityTransaction;
import javax.persistence.Persistence;

public class PersonDriver {

	public static void main(String[] args) {

		// Create EntityManagerFactory
		EntityManagerFactory emf =
				Persistence.createEntityManagerFactory("pravin");

		// Create EntityManager
		EntityManager em = emf.createEntityManager();

		// Transaction Object
		EntityTransaction et = em.getTransaction();

		// Transient Object
		Person p = new Person();

		p.setP_id(1);
		p.setpName("Pravin");
		p.setpAge(21);

		et.begin();

		/*
		 * persist()
		 * Used to save object into database.
		 */
		em.persist(p);

		et.commit();

		System.out.println("Record Inserted Successfully");
	}
}
INSERT persist() ↓ Record Created
EXTRA — Explanation
  • EntityManagerFactory is created once per persistence unit ("pravin" — the name configured in persistence.xml). It's expensive to create, so it's typically a singleton for the app.
  • EntityManager is the lightweight, per-operation interface to the persistence context (like a JDBC Connection, but object-aware).
  • Before persist(), the Person object p is in the Transient state — it exists only in Java memory, unknown to Hibernate.
  • After persist() (inside an active transaction), it becomes Persistent (Managed) — Hibernate now tracks it and will sync any further changes to the DB.
  • et.begin() / et.commit() wrap the write in a transaction — without commit(), the insert is never flushed to the database.

3. Fetch by ID — FetchById.java (find())

ORIGINAL CODE 
package com.ty;

import javax.persistence.EntityManager;
import javax.persistence.EntityManagerFactory;
import javax.persistence.Persistence;

public class FetchById {

	public static void main(String[] args) {

		EntityManagerFactory emf =
				Persistence.createEntityManagerFactory("pravin");

		EntityManager em =
				emf.createEntityManager();

		/*
		 * find()
		 * Fetches record using Primary Key.
		 */
		Person p =
				em.find(Person.class, 1);

		if (p != null) {

			System.out.println("Id : " + p.getP_id());
			System.out.println("Name : " + p.getpName());
			System.out.println("Age : " + p.getpAge());

		} else {

			System.out.println("Record Not Found");
		}
	}
}
FETCH BY ID find() ↓ Single Record
EXTRA — Explanation
  • em.find(Class, primaryKey) is the standard way to fetch by primary key. It returns null if not found (unlike getReference(), which throws EntityNotFoundException lazily).
  • find() first checks the 1st-level (session) cache before hitting the database — if the entity was already loaded/persisted in this EntityManager, no SQL is fired at all.
  • No transaction is required for a simple read — find() works outside a transaction, unlike persist()/remove() which need one.
  • The returned object is in the Persistent state — any field changes made to it later will be auto-detected (see Update below).

4. Update — UpdateById.java (Dirty Checking)

ORIGINAL CODE 
package com.ty;

import javax.persistence.EntityManager;
import javax.persistence.EntityManagerFactory;
import javax.persistence.EntityTransaction;
import javax.persistence.Persistence;

public class UpdateById {

	public static void main(String[] args) {

		EntityManagerFactory emf =
				Persistence.createEntityManagerFactory("pravin");

		EntityManager em =
				emf.createEntityManager();

		EntityTransaction et =
				em.getTransaction();

		/*
		 * Fetch Existing Record
		 */
		Person p =
				em.find(Person.class, 1);

		if (p != null) {

			p.setpName("Shravan");

			et.begin();

			/*
			 * Dirty Checking
			 * Hibernate automatically updates.
			 */

			et.commit();

			System.out.println("Record Updated");
		}
	}
}
UPDATE find() ↓ Modify Object ↓ commit()
EXTRA — Explanation: Dirty Checking
  • Notice there's no explicit em.update() or em.merge() call — the setter p.setpName("Shravan") is called before the transaction commits, on an object that's already Persistent (fetched via find()).
  • Hibernate's persistence context keeps a snapshot of the entity's state at load time. At flush/commit time it compares the current state vs the snapshot — any difference is called "dirty" and triggers an automatic UPDATE SQL statement.
  • This only works because p stays attached/managed to the same EntityManager the whole time. If you set the field after closing the EntityManager, the object becomes Detached and dirty checking won't fire — you'd need em.merge(p) instead.
  • Order matters here versus the setter placement: the field is changed before et.begin() in this code, but the change is still only flushed to the DB when et.commit() runs — Hibernate batches the dirty check to flush time, not the moment the setter is called.

5. Fetch All — FetchAll.java (JPQL)

ORIGINAL CODE 
package com.ty;

import java.util.List;

import javax.persistence.EntityManager;
import javax.persistence.EntityManagerFactory;
import javax.persistence.Persistence;
import javax.persistence.Query;

public class FetchAll {

	public static void main(String[] args) {

		EntityManagerFactory emf =
				Persistence.createEntityManagerFactory("pravin");

		EntityManager em =
				emf.createEntityManager();

		/*
		 * JPQL Query
		 * p is alias
		 */
		Query query =
				em.createQuery("select p from Person p");

		List<Person> persons =
				query.getResultList();

		for (Person p : persons) {

			System.out.println("----------------");

			System.out.println("Id : " + p.getP_id());
			System.out.println("Name : " + p.getpName());
			System.out.println("Age : " + p.getpAge());
		}
	}
}
FETCH ALL createQuery() ↓ Multiple Records
EXTRA — Explanation: JPQL
  • JPQL (Java Persistence Query Language) queries operate on entity objects and their fields, not table/column names — "select p from Person p" refers to the Person class, not the DB table.
  • p is an alias for the entity, similar to a table alias in SQL — required syntax in JPQL even for simple selects.
  • getResultList() returns a raw List — this is unchecked, so the assignment List<Person> persons = query.getResultList(); produces an unchecked-cast compiler warning (safe to ignore here, but worth knowing for interviews).
  • JPQL is database-independent — Hibernate translates it into the correct native SQL dialect at runtime, unlike a native createNativeQuery() call.

6. Delete — DeleteById.java (remove())

ORIGINAL CODE 
package com.ty;

import javax.persistence.EntityManager;
import javax.persistence.EntityManagerFactory;
import javax.persistence.EntityTransaction;
import javax.persistence.Persistence;

public class DeleteById {

	public static void main(String[] args) {

		EntityManagerFactory emf =
				Persistence.createEntityManagerFactory("pravin");

		EntityManager em =
				emf.createEntityManager();

		EntityTransaction et =
				em.getTransaction();

		Person p =
				em.find(Person.class, 1);

		if (p != null) {

			et.begin();

			/*
			 * remove()
			 * Deletes record from database.
			 */
			em.remove(p);

			et.commit();

			System.out.println("Record Deleted");
		}
	}
}
DELETE find() ↓ remove() ↓ commit()
EXTRA — Explanation
  • em.remove() only accepts a Managed entity — this is why find() is always called first to load and attach the object before removing it. You cannot pass a Transient or Detached instance directly.
  • After remove(), the entity moves to the Removed state within the persistence context; the actual DELETE SQL fires at flush/commit time, not immediately.
  • If a foreign-key constrained child record exists and cascade delete isn't configured, this will throw a ConstraintViolationException at commit time.

EXTRA — Entity Lifecycle States
  • Transient — plain Java object, not associated with any EntityManager, no row in DB. (new Person())
  • Persistent (Managed) — associated with an open EntityManager; any change is tracked and auto-synced to DB on flush.
  • Detached — was persistent, but the EntityManager was closed or the entity was evicted. Changes are no longer tracked; must call merge() to reattach.
  • Removed — scheduled for deletion; still in memory until the transaction commits.

9. Interview Q&A

INTERVIEW PREP
Q1. What is Dirty Checking in Hibernate?
Hibernate compares a managed entity's current field values against the snapshot taken when it was loaded. If they differ at flush/commit time, Hibernate automatically issues an UPDATE — no explicit save call is needed, as shown in UpdateById.java.
Q2. Why does remove() require calling find() first?
remove() only operates on managed (Persistent) entities. find() loads the object into the persistence context so Hibernate can track and later delete it correctly.
Q3. What's the difference between persist() and merge()?
persist() is for new (Transient) entities and makes them Persistent. merge() is for Detached entities — it copies their state onto a managed instance (creating one if needed) and returns that managed copy.
Q4. Why is a default (no-arg) constructor mandatory in an @Entity class?
Hibernate instantiates entities via reflection (Class.newInstance() style) before populating fields, which requires a no-arg constructor — even if the app code never calls it directly.
Q5. Does JPQL query tables or entities?
JPQL queries entity objects and their fields (e.g. Person, pName), not database table/column names. Hibernate translates the JPQL into the appropriate native SQL at runtime.
Q6. What happens if you call commit() without begin()?
It throws an IllegalStateException — a transaction must be explicitly started with et.begin() before it can be committed.
Q7. Why doesn't find() need a transaction, but persist()/remove()/updates do?
Reads don't modify data, so JPA allows them outside a transaction (though a transaction is still recommended for consistency in some providers). Any write operation must be wrapped in a transaction so it can be committed or rolled back atomically.
Q8. What is the role of EntityManagerFactory vs EntityManager?
EntityManagerFactory is a heavyweight, thread-safe factory created once per persistence unit. EntityManager is lightweight, not thread-safe, and represents one unit-of-work / persistence context — created per operation or per request.

10. Memory Tricks

CRUD → Methods: "Persist, Find, Dirty(update), Remove" — remember as "Please Find Dirty Records".
Entity states in order: Transient → Persistent → Detached → Removed — remember as "Two Pandas Danced Rapidly".
Transaction needed? Anything that writes (persist / update / remove) needs begin()+commit(). Anything that only reads (find / query) doesn't. Think: "Write = Wrap in transaction."
Dirty Checking: No save call for updates — just "get it, change it, commit it." Hibernate quietly compares old vs new snapshot at flush time, like a diff tool running in the background.
