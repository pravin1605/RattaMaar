📘 1. What is Caching in Hibernate?
🔹 Definition

Caching is a mechanism used to store frequently accessed data in memory so that Hibernate can retrieve it quickly without repeatedly accessing the database.

🔹 Interview Definition

Caching is a performance optimization technique in Hibernate that temporarily stores frequently used data in memory to reduce database hits, decrease response time, and improve application performance.

🔹 What is Cache? (Simple)

Cache is a temporary memory area where frequently used data is stored. Instead of going to the database every time, Hibernate first checks cache.

Application Request
↓
Hibernate
↓ checks first
Cache
↓ only if not in cache
PostgreSQL Database

Without Cache: Need notes → Open laptop → Search folder → Open PDF → Read (every time!)

With Cache: Need notes → Already open on screen → Read directly ✅

📖 Library Analogy

Without Cache: Need book → Go to library → Search shelf → Get book (every time!)

With Cache: Need book → Book already on desk → Read directly ✅

📘 2. Why Caching is Needed? (The Problem)

Suppose our PostgreSQL DB has student with id=101. Now we write:

Student s1 = em.find(Student.class, 101); // DB hit 1 → SELECT * FROM student WHERE id=101 Student s2 = em.find(Student.class, 101); // DB hit 2 → same query again! Student s3 = em.find(Student.class, 101); // DB hit 3 → same query again!

👉 Same data fetched repeatedly from DB → WASTEFUL!

🔹 4 Problems Without Caching:
1
DB Load Increases — DB receives same query repeatedly → overloaded
2
Network Traffic Increases — every request travels App→DB→App, consuming network
3
Response Time Increases — DB access is slower than memory access
4
Performance Decreases — app slows down, users experience delays

Imagine: 10,000 users, 1 lakh records, thousands of requests/second → disaster without cache!

📘 3. Cache Hit and Cache Miss (Very Common Interview Question)
✅ Cache HIT

When requested data is found in cache. Database is NOT accessed.

Request Data (id=101)
↓
Cache
↓
Data Found ✅
↓
Return Object (No DB)

Benefit: Fast performance — memory speed!

❌ Cache MISS

When requested data is NOT found in cache. Database is accessed.

Request Data (id=101)
↓
Cache
↓
Data NOT Found ❌
↓
Database Hit
↓
Stored In Cache

After miss: data stored in cache for next request.

Cache Hit = data found in cache → no DB access → fast. Cache Miss = data not in cache → DB accessed → data stored in cache for future requests. Goal: maximize Cache Hits, minimize Cache Misses.
📘 4. Advantages of Caching
⚡ Improves Performance

Memory access is much faster than DB access. Milliseconds vs nanoseconds.

📉 Reduces DB Hits

Fewer SQL queries executed. DB server gets less load.

🌐 Reduces Network Traffic

Less communication between app and DB server. Bandwidth saved.

📈 Improves Scalability

Application can support more concurrent users without DB overload.

🚀 Faster Response Time

Users receive data quickly. Better user experience.

💰 Cost Reduction

Fewer DB calls = less server resources = lower infrastructure cost.

📗 Level 1 — First Level Cache (L1 Cache) Default ✅ Always ON
🔹 Definition

First Level Cache is the cache associated with a single Session (Hibernate) or EntityManager (JPA). It is enabled by default — no configuration needed.

🔹 Interview Definition

First Level Cache is a Session-level cache that stores objects within a single Session/EntityManager and is enabled by default.

Scope
One Session / One EntityManager only
Default
YES — always enabled, no config needed
Shared
NO — private to one EntityManager
Stores
Entity objects
Lifetime
EntityManager created → EntityManager closed
JDBC Equivalent
Like Persistence Context within one Connection
🔹 Example:
EntityManager em = emf.createEntityManager(); Student s1 = em.find(Student.class, 101); // 1st call → Cache miss → DB hit → SELECT executed // Object stored in L1 Cache Student s2 = em.find(Student.class, 101); // 2nd call → Cache HIT → No DB hit ✅ // s1 == s2 → true (same object reference!)
🔹 Internal Working:
First Request:
find(101)
↓ Cache Empty
Database Hit → SQL executed
↓ Object returned + stored in L1
L1 Cache holds Student(101)
Second Request:
find(101)
↓ Cache HIT ✅
Object returned — NO DB query!
🔹 Limitation of L1 Cache:
EntityManager em1 = emf.createEntityManager(); em1.find(Student.class, 101); // DB hit, stored in L1 em1.close(); // L1 Cache DESTROYED! EntityManager em2 = emf.createEntityManager(); em2.find(Student.class, 101); // L1 of em1 is gone! DB hit again ❌

👉 Solution: Second Level Cache (shared across sessions)

First Level Cache is Session-level, enabled by default, private to one EntityManager. When em.find() called twice for same PK within same session — second call hits L1 cache, not DB. When EntityManager closes, L1 cache is destroyed — data must be re-fetched from DB by a new EM.
📘 Level 2 — Second Level Cache (L2 Cache) Must Enable ⚙️
🔹 Definition

Second Level Cache is a cache shared among multiple Sessions or EntityManagers. It is at the SessionFactory / EntityManagerFactory level.

Scope
SessionFactory / EntityManagerFactory (all EMs)
Default
NO — must be explicitly configured
Shared
YES — all EntityManagers share it
Stores
Entity objects
Lifetime
Application start → Application shutdown
🔹 Common Cache Providers:
  • EhCache — most commonly used with Hibernate
  • Redis — distributed cache for large apps
  • Hazelcast — distributed in-memory data grid
  • Infinispan — JBoss distributed cache
🔹 Internal Working:
User 1 (em1):
em1.find(101) → DB Hit → stored in L2
em1.close() → L1 gone, L2 survives!
User 2 (em2):
em2.find(101) → L2 Cache HIT ✅ No DB!
🔹 Configuration in persistence.xml:
<!-- Enable Second Level Cache --> <property name="hibernate.cache.use_second_level_cache" value="true"/> <!-- Specify Cache Provider --> <property name="hibernate.cache.region.factory_class" value="org.hibernate.cache.ehcache.EhCacheRegionFactory"/>
🔹 Entity must also opt-in:
@Entity @Cache(usage = CacheConcurrencyStrategy.READ_WRITE) public class Student { ... }
Second Level Cache is SessionFactory-level, shared across all sessions, NOT enabled by default. After em1 closes (L1 gone), em2 can still find data in L2 cache — no DB hit. Requires external provider (EhCache, Redis) + persistence.xml config + @Cache annotation on entity.

📙 Level 3 — Query Cache Must Enable ⚙️ | Depends on L2
🔹 Definition

Query Cache stores query results rather than entity objects. When the same JPQL/HQL query is executed again, Hibernate returns the cached result instead of hitting DB.

Stores
Query result sets (IDs / values — NOT entity objects)
Default
NO — must be enabled
Depends on
Second Level Cache — cannot work without L2
Lifetime
Application life (until data changes)
🔹 What Gets Stored?

Very Important Interview Question!

Query Cache stores: Query Result — NOT entity objects.

Example: SELECT * FROM STUDENT → stores IDs [101, 102, 103, 104]

Then uses L2 cache to fetch actual entity objects for those IDs.

📝 Query Cache Dependency Chain:
Query Cache → needs → Second Level Cache → needs → EhCache/Redis
If L2 not enabled → Query Cache will NOT work effectively.
🔹 Example:
// Without Query Cache: Query q = em.createQuery("FROM Student"); q.getResultList(); // DB hit 1 → SELECT * q.getResultList(); // DB hit 2 → same query again! // With Query Cache enabled: q.setHint("org.hibernate.cacheable", true); q.getResultList(); // DB hit 1 → result stored in QC q.getResultList(); // QC hit ✅ → No DB!
🔹 Configuration:
<!-- Enable Query Cache --> <property name="hibernate.cache.use_query_cache" value="true"/>
🔹 When Query Cache is INVALIDATED:
  • When any entity in the result is INSERT/UPDATE/DELETE
  • Hibernate automatically invalidates stale cache entries
  • Next query call fetches fresh from DB
Query Cache stores query result sets (IDs/values — not full objects). When same query runs again, result returned from cache. Query Cache depends on Second Level Cache. Must be enabled with use_query_cache=true AND each query must be marked as cacheable using setHint().
📘 EhCache — Enabling Second Level Cache (Step by Step)
🔹 Step 1: Add EhCache Dependency in pom.xml
<!-- pom.xml --> <!-- IMPORTANT: EhCache version must match --> <!-- Hibernate version! --> <dependency> <groupId>org.hibernate</groupId> <artifactId>hibernate-ehcache</artifactId> <version>5.6.15.Final</version> </dependency> <dependency> <groupId>org.hibernate</groupId> <artifactId>hibernate-core</artifactId> <version>5.6.15.Final</version> </dependency>
⚠️ Version must match! EhCache dependency version must be same as Hibernate-core version. Mismatch → runtime errors.
🔹 Step 2: Configure persistence.xml
<property name="hibernate.cache.use_second_level_cache" value="true"/> <property name="hibernate.cache.region.factory_class" value="org.hibernate.cache.ehcache .EhCacheRegionFactory"/> <!-- Optional: Enable Query Cache too --> <property name="hibernate.cache.use_query_cache" value="true"/>
🔹 Step 3: Annotate Entity with @Cache
import org.hibernate.annotations.Cache; import org.hibernate.annotations.CacheConcurrencyStrategy; @Entity @Cache(usage = CacheConcurrencyStrategy.READ_WRITE) public class Student { ... } // READ_ONLY, READ_WRITE, NONSTRICT_READ_WRITE, TRANSACTIONAL
🔹 CacheConcurrencyStrategy Options:

READ_WRITEData changes sometimesSoft locking to maintain consistency on update

🎯 Interview Answers
✅ Q: What is Caching in Hibernate?

Caching is a mechanism used to temporarily store frequently accessed data in memory so that Hibernate can retrieve data without repeatedly hitting the database. It improves application performance, reduces database load, decreases network traffic, and provides faster response time.

✅ Q: What are the Levels of Cache in Hibernate?
  1. First Level Cache — Session-level cache. Enabled by default. Available within a single EntityManager/Session. Private — not shared. Destroyed when EM closes.
  2. Second Level Cache — SessionFactory-level cache. Not enabled by default. Shared across multiple sessions. Requires external providers like EhCache or Redis. Survives session closure.
  3. Query Cache — Stores query results (not entity objects). Not enabled by default. Depends on Second Level Cache. When same query runs again, returns cached result.
✅ Q: What is Cache Hit and Cache Miss?

Cache Hit: When requested data is found in cache — no database access required. Results in fast response.

Cache Miss: When requested data is NOT found in cache — database is accessed. Data retrieved from DB and stored in cache for future requests.

🗂️ Quick Revision — All Key Points
  • Cache = temporary memory for frequently used data
  • Reduces DB hits → improves performance
  • Cache Hit = found in cache → no DB
  • Cache Miss = not in cache → DB accessed → stored in cache
  • L1 Cache = Session level | Default ON | Private | Destroyed on EM close
  • L2 Cache = SessionFactory level | Default OFF | Shared | Application lifetime
  • Query Cache = Query results | Default OFF | Depends on L2
  • Order: L1 → L2 → Query Cache → DB
  • L2 providers: EhCache (most common), Redis, Hazelcast, Infinispan
  • Enable L2: use_second_level_cache=true in persistence.xml
  • Enable QC: use_query_cache=true in persistence.xml
  • Entity needs @Cache(usage=...) for L2
  • Query needs setHint("org.hibernate.cacheable", true)
  • EhCache version must match Hibernate version!
  • L1 cannot be disabled | L2 is optional but recommended
  • Memory ~ns | DB ~ms → Cache is 1000x faster!
Three cache levels: L1 (Session, default ON, private), L2 (SessionFactory, default OFF, shared, needs EhCache/Redis), Query Cache (default OFF, stores results, needs L2). Hibernate checks L1 → L2 → QC → DB. Cache Hit = no DB; Cache Miss = DB accessed + stored in cache.
