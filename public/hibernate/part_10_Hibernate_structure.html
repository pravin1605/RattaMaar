1. Introduction

THEORY

When developing a Hibernate application, writing all the code inside a single Java class is not a good practice. As the application grows, the code becomes lengthy, difficult to understand, maintain, and debug.

To overcome this problem, Hibernate applications follow a layered architecture, where different responsibilities are divided into different classes and packages. This approach makes the project clean, reusable, scalable, and easy to maintain.

Instead of writing Entity classes, database operations, and the main execution logic in one place, we separate them into different layers such as DTO, DAO, and Driver (Controller).

This separation of responsibilities is one of the most common practices followed in enterprise-level Java applications.

2. Why Do We Need Project Structure?

THEORY

Suppose we create a Hibernate project and write everything inside one class:

public class Driver {
	public static void main(String[] args) {
		// Create Entity Object
		// Insert Data
		// Fetch Data
		// Update Data
		// Delete Data
		// Print Output
	}
}

Initially, this seems simple. But imagine the application contains:

  • 20 Entity Classes
  • 200 Database Operations
  • Thousands of lines of code

Everything inside one class becomes difficult to understand.

Problems:

  • ❌ Large code
  • ❌ Difficult debugging
  • ❌ Difficult maintenance
  • ❌ Code duplication
  • ❌ Poor readability
  • ❌ Low reusability
  • ❌ Not suitable for enterprise applications

Therefore, we divide the application into different layers.

3. What is Layered Architecture?

THEORY

Layered Architecture is a software design approach in which the application is divided into multiple layers. Each layer has a specific responsibility and communicates only with the required layer.

Instead of mixing all the logic together, every layer performs a single task. This makes the application:

  • Modular
  • Reusable
  • Easy to maintain
  • Easy to test
  • Easy to extend

5. Purpose of Each Package & Layer Responsibilities

PackageResponsibility
com.DTORepresents database tables using Entity classes.
com.DAOContains all database operations such as Insert, Fetch, Update, and Delete.
com.tyContains the Driver class with the main() method to execute the application.

DTO Layer

Responsible for:

  • Representing database tables
  • Holding data
  • Mapping Java Objects with database tables

It does not perform database operations.

DAO Layer

Responsible for:

  • Insert
  • Fetch
  • Update
  • Delete

It contains all persistence logic. It does not contain the main() method.

Driver (Controller) Layer

Responsible for:

  • Starting the application
  • Creating objects
  • Calling DAO methods
  • Displaying results

It does not contain persistence logic.

6. Execution Flow

Application Starts ↓ Driver Class Executes ↓ Creates Entity Object ↓ Calls DAO Method ↓ DAO Uses EntityManager ↓ Hibernate Generates SQL ↓ PostgreSQL Executes Query ↓ Result Returned ↓ Displayed to User

Complete Layered Flow

Driver Class ↓ LaptopDao.java ↓ EntityManager API ↓ Hibernate Framework ↓ PostgreSQL Database ↑ Laptop Entity Class

7. Real-Life Example

THEORY

Imagine an online shopping application:

Customer ↓ Website (Controller) ↓ Service Executive (DAO) ↓ Product Information (DTO) ↓ Warehouse (Database)

Explanation:

  • The Customer places a request.
  • The Website (Controller) receives the request.
  • The Service Executive (DAO) processes the request and communicates with the warehouse.
  • The Product Information (DTO) carries the product details.
  • The Warehouse (Database) stores the actual data.

Similarly, in a Hibernate application:

User ↓ Driver Class ↓ DAO Class ↓ Entity Class ↓ Database

8. Code — Laptop Entity, LaptopDao, Driverlaptop

8.1 Entity — Laptop.java (com.DTO)

ORIGINAL CODE 
package com.DTO;

import javax.annotation.processing.Generated;
import javax.persistence.Entity;
import javax.persistence.GeneratedValue;
import javax.persistence.GenerationType;
import javax.persistence.Id;

@Entity
public class Laptop {
	
	@Id
	@GeneratedValue(strategy = GenerationType.IDENTITY)
	private int id;
	@Override
	public String toString() {
		return "Laptop [id=" + id + ", name=" + name + ", price=" + price + "]";
	}
	private String name;
	private int price;
	
	public int getId() {
		return id;
	}
	public void setId(int id) {
		this.id = id;
	}
	public String getName() {
		return name;
	}
	public void setName(String name) {
		this.name = name;
	}
	public int getPrice() {
		return price;
	}
	public void setPrice(int price) {
		this.price = price;
	}

}
EXTRA — Explanation
  • @GeneratedValue(strategy = GenerationType.IDENTITY) — unlike the earlier Person entity, here the primary key id is auto-generated by the database (e.g. PostgreSQL SERIAL/identity column) rather than assigned manually in Java code.
  • GenerationType.IDENTITY relies on the database's own auto-increment column — Hibernate does an INSERT and reads back the generated key immediately (this disables JDBC batching for inserts, worth knowing for interviews).
  • toString() is overridden so System.out.println(l1) in findAll() prints a readable representation instead of the default Object.toString() hash.
  • The unused import javax.annotation.processing.Generated is unrelated to JPA's @GeneratedValue — likely an IDE auto-import mistake; it has no effect here.

8.2 DAO — LaptopDao.java (com.DAO)

ORIGINAL CODE 
package com.DAO;

import java.util.List;

import javax.persistence.EntityManager;
import javax.persistence.EntityManagerFactory;
import javax.persistence.EntityTransaction;
import javax.persistence.Persistence;

import com.DTO.Laptop;

public class LaptopDao {
	EntityManagerFactory emf = Persistence.createEntityManagerFactory("pravin");
	EntityManager em = emf.createEntityManager();
	EntityTransaction et = em.getTransaction();
	
	public void insertData(Laptop l) {
		et.begin();
		em.persist(l);
		et.commit();
		System.out.println("data inserted.....");
	}
	public void findById(int lid) {
		Laptop l =em.find(Laptop.class,lid );
		
		System.out.println(l.getId()+" "+l.getName());
		
	}
	
	public void findAll() {
		List<Laptop> l=em.createQuery("select l from Laptop l").getResultList();
		for(Laptop l1 : l) {
			System.out.println(l1);
		}
	}
	
	public void updateBrand(int id,String lbrand) {
		Laptop l =em.find(Laptop.class, id);
		l.setName(lbrand);
		et.begin();
		em.merge(l);
		et.commit();
		
	}
	
	public void replaceObject(int id,Laptop newlaptop) {
		Laptop oldlaptop = em.find(Laptop.class, id);
		et.begin();
		if(oldlaptop!=null) {
			newlaptop.setId(oldlaptop.getId());
			em.merge(newlaptop);
		}
		et.commit();
		
	}
	
	public void deletelaptop(int id) {
		Laptop l = em.find(Laptop.class, id);
		
		et.begin();
		em.remove(l);
		et.commit();
	}

}
EXTRA — Explanation
  • DAO owns the persistence resources — EntityManagerFactory, EntityManager, and EntityTransaction are instance fields, created once when a LaptopDao object is constructed, and reused across all its methods. This is different from the earlier standalone driver classes, which created a fresh EntityManager inside every main().
  • updateBrand() uses em.merge(l) even though l was just loaded via find() and is already managed — here merge() is redundant but harmless, since l is still attached (plain dirty checking, like in the earlier UpdateById example, would have worked without it).
  • replaceObject() shows a genuine, correct use of merge(): newlaptop is a separate, Detached/Transient object (passed in from outside), not the one returned by find(). Copying the old ID onto it and calling merge() tells Hibernate "treat this object's state as the new state for that row."
  • findById() and deletelaptop() don't null-check the result of find() — if the ID doesn't exist, l will be null and calling l.getId() / em.remove(l) will throw a NullPointerException. (Compare with FetchById/DeleteById from the earlier notes, which do check if (p != null).)
  • Because et (the EntityTransaction) is a single shared field, calling et.begin() twice in a row without an intervening commit()/rollback() would throw IllegalStateException: Transaction already active — safe here since each method begins and commits its own transaction before returning.

10. Interview Q&A

INTERVIEW PREP
Q1. What is layered architecture in a Hibernate application?
A design approach that divides the application into separate layers — DTO (entity/data representation), DAO (persistence logic), and Driver/Controller (execution flow) — where each layer has one responsibility and communicates only with the layer it needs.
Q2. What is the responsibility of the DTO layer?
Represents database tables as Java objects, holds data, and maps fields to columns via JPA annotations (@Entity, @Id, @GeneratedValue). It performs no database operations itself.
Q3. What is the responsibility of the DAO layer?
Contains all persistence logic — Insert, Fetch, Update, Delete — using EntityManager. It never contains the main() method.
Q4. What is the responsibility of the Driver (Controller) layer?
Starts the application, creates entity objects, calls DAO methods, and displays results. It contains no persistence logic of its own.
Q5. Why is GenerationType.IDENTITY used in the Laptop entity but not in the earlier Person entity?
Person assigned its ID manually in application code (setP_id(1)). Laptop instead delegates ID generation to the database's identity/auto-increment column via @GeneratedValue(strategy = GenerationType.IDENTITY), so the ID is created automatically on insert.
Q6. In replaceObject(), why is merge() the correct choice rather than plain dirty checking?
Dirty checking only works on entities managed by the current persistence context. newlaptop is a separate object passed in from outside — it was never loaded via find() — so it isn't managed. merge() copies its state onto (or creates) a managed entity with the matching ID.
Q7. What real-world bug exists in findById() and deletelaptop()?
Neither method null-checks the object returned by find(). If the given ID doesn't exist, find() returns null, and the next line (l.getId() or em.remove(l)) throws a NullPointerException.
Q8. Why does keeping EntityManager as an instance field in the DAO matter?
It means all methods in that LaptopDao instance share the same persistence context — entities loaded by one method stay managed and visible to later calls on the same DAO object, which is what allows dirty checking to work across method calls within the same instance.

11. Memory Tricks

DTO / DAO / Driver: "Data shape, Database actions, Directs the flow" — three D's, three jobs: DTO = what the data looks like, DAO = what you do to it, Driver = when/why you do it.
Layer flow: User → Driver → DAO → Hibernate → Database — remember as "Uncle Drives Down Highway to Destination".
merge() vs dirty checking: If the object came from find() in this same EntityManager and is still attached → just change it, dirty checking handles the rest. If the object came from outside (a new/detached instance) → use merge().
Real-world analogy: Online shopping — Customer (User) → Website (Driver/Controller) → Service Executive (DAO) → Product Info (DTO) → Warehouse (Database).
