📘 1. What is an Entity Object?

An Entity Object is a Java object whose data is stored in a database table.

Example Entity Class:
@Entity @Table(name="student") public class Student { @Id private int id; private String name; private String city; public Student() { } // Getters and Setters }
Database Table:
idnamecity
101PravinMumbai

👉 Student Java class ↔ student DB table
👉 Student object ↔ one row in table

📘 2. What is Hibernate Life Cycle?
🔹 Definition

Hibernate Life Cycle represents the different states through which an Entity Object passes during its interaction with Hibernate and the database.

🔹 Interview Definition

Hibernate Life Cycle is the journey of an Entity Object from its creation in Java memory until it is stored, managed, detached, and finally removed from the database.

🔹 Real-Life Example — Company Employee
Stage 1 — Not Employee Yet

You exist but are outside the company. Company doesn't know you.

→ Transient State

Stage 2 — Active Employee

Company hires you. Tracks attendance, salary, projects.

→ Persistent State

Stage 3 — Ex-Employee

You resign. Company no longer tracks you. Record still exists.

→ Detached State

Stage 4 — Record Deleted

Employee record permanently deleted from system.

→ Removed State

Hibernate Life Cycle is the journey of an Entity Object through 4 states: Transient (exists only in JVM), Persistent (managed by Hibernate, synced to DB), Detached (exists but not managed), and Removed (marked for deletion).

Hibernate Life Cycle | Page 2 — State 1: Transient & State 2: Persistent + Dirty Checking
📘 State 1 — TRANSIENT STATE Object in JVM only | Hibernate unaware
🔹 Definition

An object that exists only in Java memory and is NOT associated with Hibernate Session / EntityManager is called a Transient Object.

🔹 Example:
Student s = new Student(); s.setId(101); s.setName("Pravin"); s.setCity("Mumbai"); // Object created — no em.persist() yet // Object is in TRANSIENT state
🔹 Internal Situation:
Student Object (JVM Memory)
↕
Database ❌ Empty — No Record
🔹 Important Characteristics:
  • ✅ Object exists only in JVM memory
  • ❌ Hibernate does NOT know about it
  • ❌ Database row does NOT exist
  • ❌ No SQL query executed
  • ❌ Not inside Persistence Context
  • ❌ No Dirty Checking
💬 Interview Point:
Q: Is Hibernate tracking this object?
A: NO — because object is not associated with EntityManager. It is just a regular Java object.
Transient State: Object created with new keyword, exists only in JVM heap, not associated with any Hibernate Session or EntityManager, no corresponding row in DB, no SQL generated. Hibernate has zero knowledge of this object.
📘 State 2 — PERSISTENT STATE Managed by Hibernate | Synced to DB | Dirty Checking
🔹 Definition

When an object becomes associated with EntityManager / Session, Hibernate starts managing it. Such object is called a Persistent Object.

🔹 Example:
EntityManagerFactory emf = Persistence.createEntityManagerFactory("pravin"); EntityManager em = emf.createEntityManager(); em.getTransaction().begin(); Student s = new Student(); s.setId(101); s.setName("Pravin"); s.setCity("Mumbai"); em.persist(s); // NOW → PERSISTENT STATE
🔹 SQL Generated:
insert into student(id, name, city) values(101, 'Pravin', 'Mumbai');
🔹 Important Characteristics:
  • ✅ Object is managed by Hibernate
  • ✅ Hibernate tracks ALL changes
  • ✅ Object exists in database
  • ✅ Object exists in First Level Cache
  • ✅ Inside Persistence Context
  • ✅ Dirty Checking is ACTIVE
🔹 Persistence Context:

Persistence Context is a memory area managed by EntityManager. It contains all Persistent Objects.

EntityManager
↓ manages
Persistence Context
↓ contains
Persistent Objects
🔥 Very Important Concept — DIRTY CHECKING (Interviewers LOVE this question)

Suppose:

Student s = em.find(Student.class, 101); s.setCity("Pune"); // You NEVER wrote any UPDATE query! // But still DB gets updated!

Why? Because object is Persistent. Hibernate continuously monitors it. This feature is called: Dirty Checking

🔹 Dirty Checking Flow:
Persistent Object
↓
Value Changed (setCity("Pune"))
↓
Hibernate Detects Change
↓
Auto UPDATE Query Executed
update student set city='Pune' where id=101;
Persistent State: Object is associated with EntityManager, tracked by Hibernate, exists in DB and Persistence Context. DIRTY CHECKING — if you change any field of a Persistent object, Hibernate automatically generates UPDATE SQL at transaction commit — without you writing any update code!
Hibernate Life Cycle | Page 3 — State 3: Detached & State 4: Removed
📘 State 3 — DETACHED STATE Object exists | EntityManager closed | Hibernate stops tracking
🔹 Definition

When a Persistent Object loses its connection with EntityManager, it becomes Detached.

🔹 Example:
Student s = em.find(Student.class, 101); // s is PERSISTENT em.close(); // EntityManager closed // Now: Student Object STILL EXISTS // But EntityManager is CLOSED // s is now DETACHED
🔹 Internal View:
Before em.close():
Student ↔ EntityManager ✅ Connected
After em.close():
Student (exists) / EntityManager ❌ Closed
🔹 Example of Dirty Checking stopped:
s.setCity("Delhi"); // Nothing happens! // No SQL query generated. // Why? Object is DETACHED. // Hibernate is no longer managing it.
🔹 Important Characteristics:
  • ✅ Object exists in JVM memory
  • ✅ Database row still exists
  • ❌ Hibernate does NOT track changes
  • ❌ Dirty Checking is STOPPED
  • ❌ Not in Persistence Context
  • ❌ No auto SQL generation
💬 Interview Point:
Detached Objects are very common in Web Applications.
Reason: Every web request creates and closes EntityManager. Objects passed between layers become Detached.
🔹 Reattaching Detached Object — merge():

Hibernate provides merge() to reattach a Detached object:

EntityManager em2 = emf.createEntityManager(); em2.getTransaction().begin(); Student managedObj = em2.merge(s); // s (detached) → managedObj (PERSISTENT)

👉 Now object becomes Persistent again and Hibernate resumes tracking.

Detached State: Object exists in JVM and DB row exists, but EntityManager is closed — Hibernate stops tracking. setCity("Delhi") on detached object generates NO SQL. Use em.merge(obj) to reattach it to a new EntityManager and make it Persistent again.
📘 State 4 — REMOVED STATE Scheduled for deletion | DELETE SQL on commit
🔹 Definition

When Hibernate marks an object for deletion, it enters Removed State.

🔹 Example:
Student s = em.find(Student.class, 101); // s is PERSISTENT em.remove(s); // s is now in REMOVED STATE // Scheduled for deletion em.getTransaction().commit(); // NOW: DELETE SQL is sent to DB
🔹 SQL Generated:
delete from student where id=101;
🔹 Internal Working:
Persistent Object
↓ em.remove(s)
Removed State (scheduled)
↓ et.commit()
DELETE Query sent to DB
↓
DB Row Permanently Deleted ✅
🔹 Important Characteristics:
  • ✅ Object is scheduled for deletion
  • ✅ Hibernate tracks the deletion
  • ✅ Record removed after commit
  • ✅ DELETE SQL generated on commit
  • ❌ DB row deleted permanently
📝 Important:
em.remove(s) does NOT immediately delete from DB.
It marks the object for deletion — schedules it.
Actual DELETE SQL is sent to DB only when et.commit() is called.
This is consistent with transaction behavior.
📝 remove() requires Persistent object:
You cannot remove a Detached object directly. First use merge() to make it Persistent, then remove().
Removed State: em.remove(obj) schedules a Persistent object for deletion. Actual DELETE SQL is executed only on et.commit(). After commit, DB row is permanently deleted. You cannot directly remove a Detached object — must merge() it first.

🎯 Interview Answers — Most Important
✅ Q: What are the states of Hibernate Object Life Cycle?

Hibernate Entity Objects pass through four major states:

1. Transient State: Object exists only in Java memory and is not associated with Hibernate. No DB row exists. No SQL generated.

2. Persistent State: Object is associated with EntityManager/Session and Hibernate manages it. Any modifications are automatically synchronized using Dirty Checking.

3. Detached State: Object exists but is no longer associated with EntityManager. Hibernate does not track changes. Use merge() to reattach.

4. Removed State: Object is marked for deletion. Hibernate removes it from the database during transaction commit.

✅ Q: What is Dirty Checking in Hibernate?

Dirty Checking is a feature in Hibernate where it automatically detects changes made to a Persistent object and generates an UPDATE SQL query — without the developer writing any update code.

When a Persistent object's field is modified (e.g., s.setCity("Pune")), Hibernate compares the current state with the snapshot taken at load time. If different (dirty), it generates UPDATE student SET city='Pune' WHERE id=101 automatically on transaction commit.

Dirty Checking works ONLY for Persistent objects — it stops for Detached objects.

🗂️ Quick Revision — Key Rules
  • Transient = new Object() → JVM only → no DB → no tracking
  • Persistent = em.persist() → managed → DB → Dirty Checking ON
  • Detached = em.close() → exists → no tracking → Dirty Checking OFF
  • Removed = em.remove() → DELETE on commit → row gone
  • Transient → Persistent: em.persist()
  • Persistent → Detached: em.close() / em.detach()
  • Detached → Persistent: em.merge()
  • Persistent → Removed: em.remove()
  • Dirty Checking: field change → auto UPDATE — only for Persistent
  • Persistence Context = memory area inside EntityManager holding Persistent objects
  • em.remove() schedules deletion — NOT immediate — actual DELETE on commit
  • Cannot remove Detached object — must merge() first
  • Detached state common in web apps — EM created per request
  • First Level Cache = Persistence Context (Session-level cache)
  • Only Persistent objects exist in First Level Cache
4 states: Transient (JVM only) → Persistent (em.persist, managed, Dirty Checking ON) → Detached (em.close, not tracked) → Removed (em.remove, DELETE on commit). Dirty Checking = auto UPDATE when Persistent object field changes. merge() reattaches Detached to Persistent.
