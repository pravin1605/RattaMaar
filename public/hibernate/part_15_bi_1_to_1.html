1. What is Bidirectional Mapping?

THEORY — DEFINITION

Bidirectional Mapping is a relationship in Hibernate where both entity classes maintain a reference to each other.

In simple words:

  • Entity A knows Entity B.
  • Entity B also knows Entity A.

Both objects can access each other. Unlike Unidirectional Mapping, where only one entity is aware of the relationship, in Bidirectional Mapping both entities are aware of it.

Simple Definition (Interview)

"Bidirectional Mapping is a relationship in which both entity classes maintain references to each other. Therefore, navigation is possible from both sides of the relationship."

2. Real-Life Example

THEORY

Suppose a person has one passport. Similarly, every passport belongs to one person.

Person ←────────→ Passport

Person knows Passport. Passport also knows Person.

Real-Life Scenario

Pravin │ │ owns ▼ Passport

Now suppose someone asks: "Who owns Passport MH12345?" — Passport should know Person. Similarly, if someone asks "What is Pravin's Passport Number?" — Person should know Passport. So both objects require references.

4. Why Do We Need Bidirectional Mapping?

THEORY

Suppose we only have unidirectional: Person → Passport. We can easily fetch Passport using Person. But — can Passport fetch Person? No.

Now suppose police have a Passport Number and want owner details. Without Bidirectional Mapping, this is impossible directly. With Bidirectional Mapping, passport.getPerson() works immediately.

6. Important Hibernate Annotations

THEORY

1. @OneToOne

Used to establish a one-to-one relationship.

@OneToOne
private Passport passport;

Meaning: one Person has one Passport.

2. @JoinColumn

Used to create the foreign key column.

@JoinColumn(name="passport_id")

Hibernate creates passport_id inside the Person table.

3. mappedBy

One of the most important concepts in Hibernate.

7. mappedBy — Why It's Needed

THEORY — DEFINITION

mappedBy tells Hibernate that: "I am not the owner of this relationship. The other entity manages the foreign key."

@OneToOne(mappedBy="passport")
private Person person;

Meaning: Passport will not create another foreign key. It simply points to Person's mapping.

Without mappedBy

Hibernate thinks Person → Passport and Passport → Person are two different relationships.

Result: Person Table gets a passport_id column, AND Passport Table gets a person_id column — two foreign keys. Wrong design.

With mappedBy

Only one foreign key is created. Correct design.

8. Owning Side vs Inverse Side

10. Code — Person, Passport, PersonDAO, Driver

10.1 Entity — Person.java (com.DTO) — Owning Side

ORIGINAL CODE 
package com.DTO;
import javax.persistence.*;
@Entity
public class Person {

	@Id
	@GeneratedValue(strategy = GenerationType.IDENTITY)
	private int personId;

	private String personName;

	// Owning Side
	@OneToOne(cascade = CascadeType.ALL)
	@JoinColumn(name = "passport_id")
	private Passport passport;

	public int getPersonId() {
		return personId;
	}

	public void setPersonId(int personId) {
		this.personId = personId;
	}

	public String getPersonName() {
		return personName;
	}

	public void setPersonName(String personName) {
		this.personName = personName;
	}

	public Passport getPassport() {
		return passport;
	}

	public void setPassport(Passport passport) {
		this.passport = passport;
	}
}

10.2 Entity — Passport.java (com.DTO) — Inverse Side

ORIGINAL CODE 
package com.DTO;
import javax.persistence.*;
@Entity
public class Passport {

	@Id
	@GeneratedValue(strategy = GenerationType.IDENTITY)
	private int passportId;

	private String passportNumber;

	// Inverse Side
	@OneToOne(mappedBy = "passport")
	private Person person;

	public int getPassportId() {
		return passportId;
	}

	public void setPassportId(int passportId) {
		this.passportId = passportId;
	}

	public String getPassportNumber() {
		return passportNumber;
	}

	public void setPassportNumber(String passportNumber) {
		this.passportNumber = passportNumber;
	}

	public Person getPerson() {
		return person;
	}

	public void setPerson(Person person) {
		this.person = person;
	}
}
EXTRA — Explanation
  • This is the first chapter in the series where import javax.persistence.*; (a wildcard import) is used instead of listing each JPA class individually — functionally identical, just more compact.
  • cascade = CascadeType.ALL on the Person.passport field means persisting a Person automatically persists its linked Passport too — this is exactly why Driver.java only needs to call dao.insert(person) and never touches the Passport DAO-side at all.
  • mappedBy = "passport" in the Passport entity refers to the field name passport inside the Person class — not a column name or table name. This string must exactly match the owning-side field name, or Hibernate throws a mapping exception at startup.
  • Because Passport is the inverse side, changes made only on the Passport side (e.g. calling passport.setPerson(x) without also calling person.setPassport(passport)) are not persisted to the database — the inverse side is purely for in-memory navigation; only the owning side's mapping is what Hibernate actually writes to SQL.

10.3 DAO — PersonDAO.java (com.DAO)

ORIGINAL CODE 
package com.DAO;
import javax.persistence.*;
import com.DTO.Person;
public class PersonDAO {

	EntityManagerFactory emf =
			Persistence.createEntityManagerFactory("pravin");

	EntityManager em = emf.createEntityManager();

	EntityTransaction et = em.getTransaction();

	public void insert(Person person) {

		et.begin();

		em.persist(person);

		et.commit();

		System.out.println("Inserted Successfully");
	}

	public Person fetchById(int id) {

		Person person = em.find(Person.class, id);

		return person;
	}
}
EXTRA — Explanation
  • This DAO is intentionally minimal compared to earlier chapters — only insert() and fetchById() are provided, with no update/delete methods for this bidirectional example, since the chapter's focus is purely on demonstrating the owning/inverse relationship, not full CRUD.
  • Note the persistence unit name reverts to "pravin" here, matching the very first chapters (CRUD, layered architecture, One-to-One) rather than "orm" used in the Many-to-One and Many-to-Many chapters.
  • fetchById() has no null-check before returning — consistent with the minimal style of this DAO, but the caller should still check the returned Person for null before calling .getPassport() etc.

10.4 Driver — Driver.java (com.Controller)

ORIGINAL CODE 
package com.Controller;
import com.DAO.PersonDAO;
import com.DTO.Passport;
import com.DTO.Person;
public class Driver {

	public static void main(String[] args) {

		Passport passport = new Passport();
		passport.setPassportNumber("MH123456");

		Person person = new Person();
		person.setPersonName("Pravin");

		// Bidirectional Linking
		person.setPassport(passport);
		passport.setPerson(person);

		PersonDAO dao = new PersonDAO();

		dao.insert(person);
	}
}
EXTRA — Explanation
  • Unlike every earlier chapter's Driver, this one is not commented out — dao.insert(person) actually runs, since this chapter is demonstrating a single focused concept (bidirectional linking) rather than offering a menu of CRUD operations to test one at a time.
  • Both linking calls are present: person.setPassport(passport) AND passport.setPerson(person). This is essential in bidirectional mappings — setting only one side keeps the object graph consistent in memory (so both directions can be navigated via getters), even though only the owning side's assignment is what Hibernate persists as the actual foreign key.
  • If passport.setPerson(person) were omitted, the insert would still work correctly (since Person is the owning side), but calling passport.getPerson() afterward, within the same in-memory object graph before a fresh fetch, would return null — a classic bidirectional-mapping bug.

11. Extra — Gaps in This Code

⚠ WORTH KNOWING
  • No helper/convenience method to keep both sides in sync. A common real-world improvement is a method like person.setPassport(Passport p) { this.passport = p; p.setPerson(this); } that automatically updates both sides in one call, so a developer can't accidentally forget the second line (as seen manually done in Driver.java here).
  • No null-checks in PersonDAO.fetchById() — if the ID doesn't exist, em.find() returns null, and any caller chaining .getPassport() on the result would throw NullPointerException.
  • No update or delete methods in this DAO at all — worth remembering this chapter is scoped narrowly to insert + fetch, unlike the fuller DAOs in Chapters 17–19.
  • Fetching Passport independently (not shown here) would require a separate PassportDAO, since passport.getPerson() only works once the Passport is already loaded as part of a fetched Person's object graph, or fetched directly by its own ID with its person field resolved via the inverse mapping.

12. Execution Flow

Final Working Flow

13. Interview Q&A

INTERVIEW PREP
Q1. What is Bidirectional Mapping?
A relationship where both entity classes maintain a reference to each other, so navigation is possible from both sides — Entity A can reach Entity B, and Entity B can reach Entity A.
Q2. What does mappedBy do, and why is it necessary?
It tells Hibernate "I am not the owner of this relationship — the other entity manages the foreign key." Without it, Hibernate would treat both sides as separate relationships and create two foreign key columns instead of one, which is incorrect.
Q3. What is the "owning side" and how do you identify it in code?
The entity that carries @JoinColumn — here, Person, since it has @JoinColumn(name = "passport_id"). The owning side is what Hibernate actually persists as the real foreign key relationship.
Q4. What is the "inverse side"?
The entity that uses mappedBy instead of @JoinColumn — here, Passport. It doesn't own the relationship; it only points back to the owning side's mapping for read/navigation purposes.
Q5. Why does the Driver call both person.setPassport(passport) and passport.setPerson(person)?
To keep the in-memory object graph consistent on both sides, so both person.getPassport() and passport.getPerson() work correctly for the objects currently held in memory. Only the owning side's assignment is what actually gets persisted as the foreign key, but skipping the inverse-side assignment would leave the in-memory graph inconsistent.
Q6. If you only called person.setPassport(passport) and skipped passport.setPerson(person), would the insert still work?
Yes — since Person is the owning side, Hibernate would still correctly persist the foreign key. But passport.getPerson() on that same in-memory passport object (before a fresh database fetch) would incorrectly return null.
Q7. What's the key difference between Unidirectional and Bidirectional mapping (interview-ready answer)?
"In Unidirectional Mapping, only one entity maintains the relationship reference, so navigation is possible in only one direction. In Bidirectional Mapping, both entities maintain references to each other. One entity becomes the owning side using @JoinColumn, while the other becomes the inverse side using mappedBy, ensuring only one foreign key is created and avoiding redundant relationships."
Q8. Why must the string passed to mappedBy exactly match a field name?
Because mappedBy = "passport" is Hibernate's way of pointing at the actual Java field (private Passport passport;) on the owning entity that defines the relationship — it's resolved via reflection at startup, so a typo or mismatch causes a mapping exception when the EntityManagerFactory is created.

14. Memory Tricks

Owning vs Inverse: "Owner has the Column (@JoinColumn), Inverse just Points (mappedBy)." Only the owning side's field is what Hibernate actually writes to SQL.
mappedBy value = field name, not column name. mappedBy = "passport" points at the passport field inside Person — never a database column.
Always set both sides in bidirectional code — set the owning side for persistence to work, and set the inverse side so in-memory navigation (.getX() from either direction) doesn't silently return null.
No mappedBy = double trouble. Forgetting mappedBy on one side makes Hibernate think there are two separate relationships — resulting in two foreign key columns instead of one, and a broken/duplicated design.
