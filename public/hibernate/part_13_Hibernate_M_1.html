1. What is Many-to-One Mapping?

THEORY — DEFINITION

Many-To-One mapping represents a relationship where many records of one table are associated with one record of another table.

In simple words: many child objects can belong to one parent object.

2. Real-Life Example

THEORY

Consider a Banking System. One bank can have many accounts.

Bank : SBI ├── Account 1 ├── Account 2 └── Account 3

Here: One Bank, Many Accounts. So the relationship is:

Many Accounts → One Bank

4. Why Many-to-One is Needed?

THEORY

Without mapping, we would have to manually store and manage foreign keys. Hibernate automatically:

  • Creates relationships.
  • Maintains foreign keys.
  • Fetches related objects.
  • Reduces SQL coding.

7.1 Entity — Bank.java (com.DTO) — the "One" side

ORIGINAL CODE 
package com.DTO;

import javax.persistence.Entity;
import javax.persistence.GeneratedValue;
import javax.persistence.GenerationType;
import javax.persistence.Id;

@Entity
public class Bank {

	// Primary Key
	@Id
	@GeneratedValue(strategy = GenerationType.IDENTITY)
	private int bankId;

	// Bank Name
	private String bankName;

	// Getter and Setter
	public int getBankId() {
		return bankId;
	}

	public void setBankId(int bankId) {
		this.bankId = bankId;
	}

	public String getBankName() {
		return bankName;
	}

	public void setBankName(String bankName) {
		this.bankName = bankName;
	}

	// Optional toString()
	@Override
	public String toString() {
		return "Bank [bankId=" + bankId + ", bankName=" + bankName + "]";
	}

}

7.2 Entity — Account.java (com.DTO) — the "Many" side

ORIGINAL CODE 
package com.DTO;

import javax.persistence.CascadeType;
import javax.persistence.Entity;
import javax.persistence.FetchType;
import javax.persistence.GeneratedValue;
import javax.persistence.GenerationType;
import javax.persistence.Id;
import javax.persistence.ManyToOne;

@Entity
public class Account {

	// Primary Key
	@Id
	@GeneratedValue(strategy = GenerationType.IDENTITY)
	private int accountId;

	// Account Name
	private String accountName;

	/*
	 * Many Accounts
	 *        ↓
	 *      One Bank
	 */

	@ManyToOne(
			cascade = CascadeType.ALL,
			fetch = FetchType.LAZY)

	private Bank bank;

	// Getter Setter

	public int getAccountId() {
		return accountId;
	}

	public void setAccountId(int accountId) {
		this.accountId = accountId;
	}

	public String getAccountName() {
		return accountName;
	}

	public void setAccountName(String accountName) {
		this.accountName = accountName;
	}

	public Bank getBank() {
		return bank;
	}

	public void setBank(Bank bank) {
		this.bank = bank;
	}

	@Override
	public String toString() {
		return "Account [accountId=" + accountId +
				", accountName=" + accountName + "]";
	}

}
EXTRA — Explanation
  • This is the mirror image of the earlier Company/Employee (One-to-Many) chapter — here the @ManyToOne annotation sits on the "many" side (Account), directly on a single Bank bank field, not a collection. This is the more common, simpler direction to model in Hibernate — the "many" side naturally owns the foreign key.
  • No @JoinColumn is specified — Hibernate will default to a foreign key column named bank_bankId in the Account table (as shown in the Database Diagram above), based on the referenced entity name + its primary key field.
  • cascade = CascadeType.ALL is a key difference from the earlier Car/Engine and Company/Employee examples, which had no cascade at all. Here, persisting/merging/removing an Account automatically cascades the same operation to its linked Bank — this is exactly why insertData() below still explicitly calls manager.persist(account.getBank()) too, which is actually redundant given the cascade (though harmless).
  • fetch = FetchType.LAZY means the Bank object is not loaded from the database immediately when an Account is fetched — it's only loaded the first time account.getBank() is actually called. This is more efficient but means getBank() must be called while the EntityManager/session is still open, or it throws LazyInitializationException.
  • @ManyToOne's default fetch type is actually EAGER (unlike @OneToMany, which defaults to LAZY) — so explicitly setting FetchType.LAZY here is a deliberate override of the default, worth remembering for interviews.

7.3 DAO — AccountDAO.java (com.DAO)

ORIGINAL CODE 
package com.DAO;

import java.util.List;

import javax.persistence.EntityManager;
import javax.persistence.EntityManagerFactory;
import javax.persistence.EntityTransaction;
import javax.persistence.Persistence;
import javax.persistence.Query;

import com.DTO.Account;
import com.DTO.Bank;

public class AccountDAO {

	// Create EntityManagerFactory
	EntityManagerFactory factory =
			Persistence.createEntityManagerFactory("orm");

	// Create EntityManager
	EntityManager manager =
			factory.createEntityManager();

	// Create Transaction
	EntityTransaction transaction =
			manager.getTransaction();

	// =========================
	// INSERT
	// =========================

	public void insertData(List<Account> accounts) {

		transaction.begin();

		for (Account account : accounts) {

			manager.persist(account);

			manager.persist(account.getBank());

		}

		transaction.commit();

		System.out.println("Inserted Successfully");

	}

	// =========================
	// FETCH BY ID
	// =========================

	public Account fetchById(int id) {

		Account account =
				manager.find(Account.class, id);

		if (account != null) {

			System.out.println("Account Id : "
					+ account.getAccountId());

			System.out.println("Account Name : "
					+ account.getAccountName());

			System.out.println("Bank Name : "
					+ account.getBank().getBankName());

		}

		return account;

	}

	// =========================
	// FETCH ALL
	// =========================

	public List<Account> fetchAll() {

		Query query =
				manager.createQuery("SELECT a FROM Account a");

		List<Account> accounts =
				query.getResultList();

		for (Account account : accounts) {

			System.out.println();

			System.out.println(account.getAccountId());

			System.out.println(account.getAccountName());

			System.out.println(account.getBank().getBankName());

		}

		return accounts;

	}

	// =========================
	// UPDATE
	// =========================

	public void update(int accountId,
					   String accountName,
					   String bankName) {

		Account account =
				manager.find(Account.class, accountId);

		if (account != null) {

			account.setAccountName(accountName);

			account.getBank().setBankName(bankName);

			transaction.begin();

			manager.merge(account);

			manager.merge(account.getBank());

			transaction.commit();

			System.out.println("Updated Successfully");

		}

	}

	// =========================
	// DELETE ACCOUNT
	// =========================

	public void deleteAccount(int accountId) {

		Account account =
				manager.find(Account.class, accountId);

		if (account != null) {

			transaction.begin();

			manager.remove(account);

			transaction.commit();

			System.out.println("Account Deleted");

		}

	}

	// =========================
	// DELETE ACCOUNT & BANK
	// =========================

	public void deleteBoth(int accountId) {

		Account account =
				manager.find(Account.class, accountId);

		if (account != null) {

			Bank bank = account.getBank();

			transaction.begin();

			account.setBank(null);

			manager.remove(account);

			if (manager.contains(bank)) {

				manager.remove(bank);

			}

			transaction.commit();

			System.out.println("Account and Bank Deleted");

		}

	}

}
EXTRA — Explanation
  • insertData() loops over a List<Account> and persists each — since Account.bank uses CascadeType.ALL, the explicit manager.persist(account.getBank()) call is technically redundant (persisting the account alone would cascade to its bank), but it's harmless and explicit.
  • deleteBoth() is the most interesting method here. It calls account.setBank(null) before removing the account — this breaks the in-memory link so the later manager.contains(bank) check still has a valid reference to test, while avoiding any cascade-triggered double-removal confusion from removing the account first while it still pointed at the bank.
  • manager.contains(bank) checks whether bank is still a managed entity in the current persistence context before trying to remove it — a defensive check, since calling remove() on a detached entity throws IllegalArgumentException.
  • This is the first DAO across all these notes to use manager.contains() — a genuinely good practice worth remembering for interviews and for your own code going forward.

8. Bugs & Gotchas in This Code

⚠ BUGS — Worth Knowing for Debugging & Interviews
  • FetchType.LAZY + printing getBank().getBankName() outside a transaction: in fetchById() and fetchAll(), account.getBank() is called to print the bank name. Since fetch is LAZY, this triggers an on-demand DB query — it will only work correctly while the EntityManager/session is still open. If this DAO's manager were ever closed before these getters ran, it would throw LazyInitializationException. It works here only because manager is a long-lived instance field, never explicitly closed.
  • update() calls both merge() and mutates in place: account was loaded via find() (so it's already managed and dirty checking alone would work), yet the code also explicitly calls manager.merge(account) and manager.merge(account.getBank()). This is redundant but not wrong — merge on an already-managed entity is a safe no-op beyond returning the same managed instance.
  • Cascade double-effect risk in deleteBoth(): because Account.bank has CascadeType.ALL (which includes REMOVE), simply calling manager.remove(account) while it still referenced its bank would already cascade-delete the Bank automatically. The code avoids this by nulling the reference first (account.setBank(null)) before removing the account, then manually removing the bank separately — a deliberate workaround to control the deletion order rather than trust the cascade.
  • No null-check on the DAO's return value used inside Driver isn't an issue here since all DAO calls are commented out — but as usual, none of the DAO methods guard against a missing bank reference if an Account were ever inserted without one.

9. Execution Flow

Driver Creates Bank + Accounts ↓ Accounts Share Same Bank Reference ↓ AccountDAO.insertData() ↓ persist(account) → cascades to Bank (CascadeType.ALL) ↓ Hibernate Generates SQL ↓ Database: Bank row + Account rows (with bank_bankId FK) ↓ fetchById() / fetchAll() ↓ getBank() triggers LAZY load if not already fetched ↓ Displayed to User

10. Interview Q&A

INTERVIEW PREP
Q1. What is Many-to-One mapping? Give the example from this code.
Many records of one table associate with one record of another table — many child objects belong to one parent. Here, many Accounts belong to one Bank, modeled with @ManyToOne private Bank bank; inside Account.
Q2. Which side holds the foreign key in a Many-to-One relationship, and why?
The "many" side — here, Account — holds the foreign key (bank_bankId), because each Account row needs to point to exactly one Bank row, while a Bank row is referenced by potentially many Account rows.
Q3. What is the default fetch type for @ManyToOne, and what does this code do differently?
The JPA default for @ManyToOne is FetchType.EAGER. This code explicitly overrides it to FetchType.LAZY, so the associated Bank is only loaded from the database when getBank() is actually called.
Q4. What risk does FetchType.LAZY introduce, and how is it avoided here?
If the entity manager/session is closed before the lazy field is accessed, calling the getter throws LazyInitializationException. It's avoided here because the DAO's manager is a long-lived instance field that stays open for the DAO's lifetime.
Q5. What does CascadeType.ALL do on the @ManyToOne field here?
It propagates persist, merge, remove (and other) operations performed on an Account to its associated Bank automatically — so saving or deleting an Account can also save or delete its linked Bank without a separate explicit call.
Q6. Why does deleteBoth() call account.setBank(null) before removing the account?
To break the object reference before removal so the code can control bank deletion explicitly and safely, rather than relying on CascadeType.ALL to auto-delete the Bank as a side effect of removing the Account — giving predictable, intentional control over the deletion order.
Q7. What does manager.contains(bank) check, and why is it used before removing?
It checks whether bank is currently a managed entity within the persistence context. It's used defensively because calling remove() on a detached (non-managed) entity throws IllegalArgumentException.
Q8. How does this Many-to-One example relate to the earlier One-to-Many (Company/Employee) example?
They represent the same kind of relationship shape from opposite sides. Company/Employee modeled it as One-to-Many with @OneToMany + @JoinColumn on the "one" side (Company). Bank/Account instead models it as Many-to-One with @ManyToOne directly on the "many" side (Account) — generally the simpler, more natural direction to implement in Hibernate.

11. Memory Tricks

Many-to-One = "Many kids, one parent." The FK always lives on the "many" (child) side — Account holds bank_bankId, not the other way around.
Default fetch types: "ManyToOne is Mostly Eager (default EAGER); OneToMany is Often Lazy (default LAZY)." Remember it flips depending on which side you're on.
manager.contains(entity): "Is it still in the room?" — checks if an entity is managed before you try to remove/act on it, avoiding IllegalArgumentException on detached entities.
Cascade ALL + manual removal order: If cascade will auto-delete a child, and you want to control that yourself, break the reference first (setX(null)) before removing the parent — exactly what deleteBoth() does.
