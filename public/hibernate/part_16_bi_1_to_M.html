1. What is Bidirectional One-to-Many?

THEORY

This chapter revisits the One-to-Many relationship from Chapter 17 (Company/Employee), but this time makes it bidirectional — both sides know about each other, so navigation works both ways:

  • department.getEmployees() — navigate Parent → Children
  • employee.getDepartment() — navigate Child → Parent

This is the enterprise-standard way to model One-to-Many in Hibernate: the "many" side (Employee) holds the actual foreign key via @ManyToOne, and the "one" side (Department) uses @OneToMany(mappedBy = ...) to expose the reverse collection without creating a redundant join table or second foreign key.

Department │ ├── Employee 1 (Pravin) ├── Employee 2 (Mayuresh) └── Employee 3 (Shravan) department.getEmployees() → [e1, e2, e3] e1.getDepartment() → department

4. Code — Department, Employee, DepartmentDAO, Driver

4.1 Entity — Department.java (com.DTO) — Parent / Inverse Side

ORIGINAL CODE 
package com.DTO;

import java.util.List;

import javax.persistence.CascadeType;
import javax.persistence.Entity;
import javax.persistence.FetchType;
import javax.persistence.GeneratedValue;
import javax.persistence.GenerationType;
import javax.persistence.Id;
import javax.persistence.OneToMany;

@Entity
public class Department {

	// Primary Key
	@Id
	@GeneratedValue(strategy = GenerationType.IDENTITY)
	private int departmentId;

	// Department Name
	private String departmentName;

	/*
	 * One Department
	 *        ↓
	 * Many Employees
	 *
	 * mappedBy = "department"
	 * tells Hibernate that Employee owns the relationship.
	 */

	@OneToMany(
			mappedBy = "department",
			cascade = CascadeType.ALL,
			fetch = FetchType.EAGER)

	private List<Employee> employees;

	// ======================
	// Getter Setter
	// ======================

	public int getDepartmentId() {
		return departmentId;
	}

	public void setDepartmentId(int departmentId) {
		this.departmentId = departmentId;
	}

	public String getDepartmentName() {
		return departmentName;
	}

	public void setDepartmentName(String departmentName) {
		this.departmentName = departmentName;
	}

	public List<Employee> getEmployees() {
		return employees;
	}

	public void setEmployees(List<Employee> employees) {
		this.employees = employees;
	}

	@Override
	public String toString() {
		return "Department [departmentId=" + departmentId +
				", departmentName=" + departmentName + "]";
	}

}

4.2 Entity — Employee.java (com.DTO) — Child / Owning Side

ORIGINAL CODE 
package com.DTO;

import javax.persistence.Entity;
import javax.persistence.GeneratedValue;
import javax.persistence.GenerationType;
import javax.persistence.Id;
import javax.persistence.JoinColumn;
import javax.persistence.ManyToOne;

@Entity
public class Employee {

	// Primary Key
	@Id
	@GeneratedValue(strategy = GenerationType.IDENTITY)
	private int employeeId;

	private String employeeName;

	private double salary;

	/*
	 * Many Employees
	 *        ↓
	 * One Department
	 *
	 * Employee is the Owning Side.
	 */

	@ManyToOne
	@JoinColumn(name = "department_id")
	private Department department;

	// ======================
	// Getter Setter
	// ======================

	public int getEmployeeId() {
		return employeeId;
	}

	public void setEmployeeId(int employeeId) {
		this.employeeId = employeeId;
	}

	public String getEmployeeName() {
		return employeeName;
	}

	public void setEmployeeName(String employeeName) {
		this.employeeName = employeeName;
	}

	public double getSalary() {
		return salary;
	}

	public void setSalary(double salary) {
		this.salary = salary;
	}

	public Department getDepartment() {
		return department;
	}

	public void setDepartment(Department department) {
		this.department = department;
	}

	@Override
	public String toString() {
		return "Employee [employeeId=" + employeeId +
				", employeeName=" + employeeName +
				", salary=" + salary + "]";
	}

}
EXTRA — Explanation
  • This is a direct structural upgrade of Chapter 17's Company/Employee: there, Employee had no back-reference to Company (unidirectional). Here, Employee gets a proper @ManyToOne Department department field, making full bidirectional navigation possible.
  • mappedBy = "department" on the Department side refers to the field name department inside Employee — same rule as Chapter 20's Person/Passport example.
  • cascade = CascadeType.ALL combined with fetch = FetchType.EAGER on the Department.employees field means: persisting/removing a Department cascades to all its Employees automatically, and fetching a Department always eagerly loads its full Employee list in the same query/round-trip.
  • No cascade is specified on the Employee.department field (the owning side) — cascade is only configured on the Department side here, which is the more common real-world direction (parent operations cascade to children, not the other way — you generally don't want deleting one Employee to also delete the whole Department).

4.3 DAO — DepartmentDAO.java (com.DAO)

ORIGINAL CODE 
package com.DAO;

import java.util.List;

import javax.persistence.EntityManager;
import javax.persistence.EntityManagerFactory;
import javax.persistence.EntityTransaction;
import javax.persistence.Persistence;

import com.DTO.Department;
import com.DTO.Employee;

public class DepartmentDAO {

	EntityManagerFactory emf =
			Persistence.createEntityManagerFactory("pravin");

	EntityManager em =
			emf.createEntityManager();

	EntityTransaction et =
			em.getTransaction();

	// ===========================
	// INSERT
	// ===========================

	public void insertDepartment(Department department) {

		et.begin();

		em.persist(department);

		et.commit();

		System.out.println("Department Inserted Successfully.");

	}

	// ===========================
	// FETCH BY ID
	// ===========================

	public void fetchById(int id) {

		Department department =
				em.find(Department.class, id);

		System.out.println(department);

		for (Employee employee : department.getEmployees()) {

			System.out.println(employee);

		}

	}

	// ===========================
	// FETCH ALL
	// ===========================

	public void fetchAll() {

		List<Department> departments =
				em.createQuery("SELECT d FROM Department d", Department.class)
						.getResultList();

		for (Department department : departments) {

			System.out.println();

			System.out.println(department);

			for (Employee employee : department.getEmployees()) {

				System.out.println(employee);

			}

		}

	}

	// ===========================
	// UPDATE
	// ===========================

	public void updateDepartment(int deptId,
								 String deptName) {

		Department department =
				em.find(Department.class, deptId);

		if (department != null) {

			department.setDepartmentName(deptName);

			et.begin();

			em.merge(department);

			et.commit();

			System.out.println("Department Updated.");

		}

	}

	// ===========================
	// UPDATE EMPLOYEE
	// ===========================

	public void updateEmployee(int empId,
							   String name,
							   double salary) {

		Employee employee =
				em.find(Employee.class, empId);

		if (employee != null) {

			employee.setEmployeeName(name);

			employee.setSalary(salary);

			et.begin();

			em.merge(employee);

			et.commit();

			System.out.println("Employee Updated.");

		}

	}

	// ===========================
	// DELETE EMPLOYEE
	// ===========================

	public void removeEmployee(int empId) {

		Employee employee =
				em.find(Employee.class, empId);

		if (employee != null) {

			Department department =
					employee.getDepartment();

			department.getEmployees().remove(employee);

			et.begin();

			em.remove(employee);

			et.commit();

			System.out.println("Employee Deleted.");

		}

	}

	// ===========================
	// DELETE DEPARTMENT
	// ===========================

	public void removeDepartment(int deptId) {

		Department department =
				em.find(Department.class, deptId);

		if (department != null) {

			et.begin();

			em.remove(department);

			et.commit();

			System.out.println("Department Deleted.");

		}

	}

}
EXTRA — Explanation
  • This is the fullest DAO in the whole mapping series — it covers insert, fetch by ID, fetch all, update on both sides, delete employee, and delete department, all in one class.
  • fetchAll() uses the typed query form: em.createQuery("SELECT d FROM Department d", Department.class) — passing Department.class as a second argument avoids the unchecked-cast warning seen in earlier chapters' List<X> = query.getResultList() pattern (e.g. Chapter 15/17's FetchAll), since the compiler now knows the result type at compile time.
  • removeEmployee() does something important and correct: before removing the Employee entity, it calls department.getEmployees().remove(employee) to also take the employee out of the Department's in-memory collection. This keeps the parent's cached/loaded collection consistent with the database after the employee is deleted — skipping this step could leave a stale reference to a deleted Employee sitting inside an already-loaded Department object.
  • removeDepartment() relies entirely on cascade = CascadeType.ALL to also remove all associated Employees — no explicit employee-removal loop is needed, unlike the manual two-step deletes seen in chapters without cascade (e.g. Chapter 17's Company/Employee, Chapter 16's Car/Engine).

EXTRA — Explanation
  • The Driver explicitly labels the two linking directions with comments — // Child → Parent (e1.setDepartment(department) etc.) and // Parent → Children (department.setEmployees(employees)) — making this the clearest example yet in these notes of what "keeping both sides in sync" looks like in practice for a collection-based bidirectional relationship.
  • Unlike e1/e2/e3 in Chapter 19's Student example, each Employee here gets its own individual object — there's no shared-reference bug like the one flagged in the Many-to-Many chapter's Driver.
  • Because Department.employees uses CascadeType.ALL, calling dao.insertDepartment(department) alone (if uncommented) is sufficient to persist the Department and all three Employees together — no separate employee-insertion loop is needed, unlike Chapter 17's insertCompany() equivalent pattern seen in other DAOs without cascade.

5. Author's Note — Enterprise-Style Callout

📝 NOTE — from your source material

This is the recommended enterprise-style implementation for Bidirectional One-to-Many:

  • Employee is the Owning Side because it contains @ManyToOne and @JoinColumn.
  • Department is the Inverse Side because it uses mappedBy = "department".
  • With cascade = CascadeType.ALL, calling em.persist(department) automatically persists all associated employees, so you don't need to call persist() for each employee individually. This is the approach you'll commonly see in real Hibernate applications.

6. Extra — Gaps & Gotchas in This Code

⚠ WORTH KNOWING
  • No null-check on department in fetchById() — unlike updateDepartment()/removeDepartment(), which do check if (department != null), fetchById() immediately calls System.out.println(department) and then loops over department.getEmployees() without checking for null first — a missing ID would throw NullPointerException.
  • No helper method to keep both sides in sync (same gap noted in Chapter 20) — the Driver manually sets both e1.setDepartment(department) and department.setEmployees(employees). A convenience method like department.addEmployee(Employee e) { employees.add(e); e.setDepartment(this); } would make this less error-prone for future additions.
  • removeEmployee()'s manual list removal is necessary specifically because fetch = FetchType.EAGER: since the Department's employee list is often already loaded in memory (eagerly), removing the employee from that in-memory list keeps it consistent with the database. If fetch were LAZY and the collection hadn't been loaded yet, this line would trigger a lazy-load fetch just to remove one element — worth knowing as a subtle performance consideration.
  • The Department's employees field could be null if a Department is ever created without calling setEmployees() — none of the DAO methods guard against a null list before iterating.

8. Execution Flow

Driver Creates Department + Employees ↓ Link Child → Parent (each Employee.setDepartment) ↓ Link Parent → Children (Department.setEmployees) ↓ DepartmentDAO.insertDepartment() ↓ persist(department) → cascades to all Employees (CascadeType.ALL) ↓ Hibernate Generates SQL ↓ Database: Department row + Employee rows (with department_id FK) ↓ fetchById() / fetchAll() ↓ Employees EAGER-loaded automatically with Department ↓ Displayed to User

9. Interview Q&A

INTERVIEW PREP
Q1. In this Department/Employee example, which side owns the relationship, and why?
Employee owns it, because it carries @ManyToOne with @JoinColumn(name = "department_id") — the actual foreign key column that Hibernate writes to SQL.
Q2. What does Department use instead of @JoinColumn, and why?
It uses @OneToMany(mappedBy = "department") — since Department is the inverse side, it doesn't own a foreign key; it simply exposes the reverse collection view by pointing at the department field on the owning Employee entity.
Q3. Why does removeEmployee() call department.getEmployees().remove(employee) before removing the employee itself?
To keep the in-memory Department object's already-loaded (EAGER) employee collection consistent with the database after deletion — otherwise the Department object could still reference a now-deleted Employee in its cached list.
Q4. Why doesn't removeDepartment() need to manually delete each Employee first?
Because Department.employees is configured with cascade = CascadeType.ALL, which includes REMOVE — removing the Department automatically cascades the removal to all its associated Employees.
Q5. How does this chapter's design differ from Chapter 17's Company/Employee mapping?
Chapter 17 was unidirectional — Employee had no reference back to Company, and Company used @JoinColumn directly on its @OneToMany collection (with no cascade). This chapter is bidirectional and follows the recommended enterprise pattern: the "many" side (Employee) owns the foreign key via @ManyToOne, and the "one" side (Department) uses mappedBy plus cascade for automatic parent-to-child persistence and deletion.
Q6. What's the benefit of the typed query form em.createQuery("SELECT d FROM Department d", Department.class) over the untyped form used in earlier chapters?
Passing the entity class as a second argument gives a compile-time-checked, typed TypedQuery<Department>, avoiding the unchecked-cast compiler warning that comes with assigning the raw getResultList() to a generic List<T> without specifying the type in the query itself.
Q7. If fetch = FetchType.LAZY were used instead of EAGER on Department.employees, what would change?
The Employee list wouldn't be loaded automatically when a Department is fetched — it would only load the first time department.getEmployees() is actually called, and only while the EntityManager/session is still open (otherwise it would throw LazyInitializationException).

10. Memory Tricks

Enterprise pattern rule of thumb: "Many side owns the key (@ManyToOne + @JoinColumn), One side just watches (@OneToMany + mappedBy)." This is the recommended real-world direction for bidirectional One-to-Many.
Cascade lives on the parent, not the child: CascadeType.ALL sits on Department.employees, not on Employee.department — parent operations cascade down to children, not the other way around.
Deleting a child from a loaded EAGER collection: always remove it from the parent's in-memory list too (parent.getChildren().remove(child)) before/alongside em.remove(child), or the parent object can hold a stale reference.
