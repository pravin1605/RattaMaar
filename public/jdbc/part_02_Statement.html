✅ Step 1 — Load and Register the Driver
// Step 1: Load and Register the Driver // Class is a predefined class in java.lang package // forName() is a static method used to load the driver class into memory Class.forName("org.postgresql.Driver");
📖 Line-by-Line Explanation
Class
Predefined class in java.lang package. Represents runtime metadata of a class — name, methods, constructors.
forName()
Static method of Class. Takes FQCN as String. Loads the specified class into JVM memory at runtime.
"org.postgresql.Driver"
Fully Qualified Class Name (FQCN) of PostgreSQL driver. org=organization, postgresql=package, Driver=class.
🔹 What happens internally when this line runs?
  1. JVM searches org.postgresql.Driver class in the classpath
  2. Loads it into JVM memory
  3. Executes the static block inside the PostgreSQL driver class
  4. Static block internally calls DriverManager.registerDriver(new Driver())
  5. Driver is now registered — ready to accept connections
🔹 Static block inside PostgreSQL Driver (Internal Code)
static { DriverManager.registerDriver(new Driver()); }

👉 This runs automatically when the class is loaded by JVM. You do NOT need to call it manually.

🔹 Alternative Way (manual registration)
Driver d = new Driver(); DriverManager.registerDriver(d);

👉 Both approaches achieve the same result — driver gets registered with DriverManager.

⚠️ Exception: If PostgreSQL JDBC JAR file is not added to the project classpath, ClassNotFoundException is thrown.
Fix: Add postgresql-42.x.x.jar to build path / dependencies.
📝 Note — Modern Java (JDBC 4.0+): From Java 6 onwards, Class.forName() is not mandatory. JDBC 4.0 introduced auto-loading of drivers using Java's ServiceLoader mechanism — the driver is auto-detected from the JAR's META-INF/services file. But we still write it for clarity and older compatibility.
Class.forName() dynamically loads the PostgreSQL driver class into JVM. Its static block auto-registers with DriverManager. From JDBC 4.0 onwards, driver auto-loads from classpath, but Class.forName() is still written for explicit clarity.

🔹 What is Connection interface?
  • Interface in java.sql package
  • Represents a live session between Java app and DB
  • Without connection → no SQL execution possible
  • It is the entry point to all DB operations
Common Methods of Connection:
createStatement() → creates Statement object
prepareStatement(sql) → creates PreparedStatement
setAutoCommit(false) → disables auto-commit
commit() → commits transaction
rollback() → rolls back transaction
close() → ends DB session
🔹 What is a Factory Method?

👉 getConnection() is called a static factory method because:

  • It is static — called on class, not object
  • It creates and returns an object (Connection) without exposing how it is created internally
  • The actual object returned is an implementation class (like PgConnection), not Connection itself — because Connection is an interface
🔹 What happens internally when getConnection() runs?
  1. DriverManager loops through all registered drivers
  2. Checks which driver accepts the given URL (jdbc:postgresql://...)
  3. PostgreSQL driver accepts it → creates a connection
  4. Returns a Connection object (actually PgConnection under the hood)
⚠️ Port Note: Default PostgreSQL port is 5432. In this program, port 5433 is used — this means PostgreSQL was configured or installed on a non-default port. Always match the port with your PostgreSQL installation.
⚠️ SQLException Causes: Wrong URL → SQLException | Wrong username/password → SQLException | DB server not running → SQLException | Network issue → SQLException
DriverManager.getConnection() is a static factory method that internally loops through all registered drivers, matches the URL to the correct driver, and returns a Connection object representing a live database session.

🔹 What is Statement interface?
  • Interface in java.sql
  • Used to send static SQL queries to database
  • SQL is written as a hardcoded String
  • DB compiles query every single time it runs
🔹 Methods of Statement:

executeQuery(sql) → SELECT; returns ResultSet
executeUpdate(sql) → DML; returns int (rows)
close() → releases Statement resources
⚠️ Disadvantages of Statement: ❌ Prone to SQL Injection (user input directly in SQL string) | ❌ Slower — DB compiles SQL on every call | ❌ Not reusable — new compilation each time | ✅ Use PreparedStatement in real projects for security + performance.
createStatement() is a non-static (instance) method of the Connection interface. It returns a Statement object. Statement is an interface in java.sql used to send hardcoded SQL queries to the database — it is prone to SQL Injection and slower due to no pre-compilation.

🔹 What is execute() method?
  • Non-static (instance) method of Statement interface
  • Can execute any SQL statement — DDL, DML, DQL

    • false → query is DML (INSERT/UPDATE/DELETE) — no ResultSet

⚠️ Why execute() and not executeUpdate() here?
Both work for INSERT. executeUpdate() is more appropriate for DML (returns int = rows affected). execute() is more generic — works for any SQL. Here execute() is used since the return value (boolean) is not being captured or used.
execute() is a non-static method of the Statement interface that can execute any SQL statement. For DML operations like INSERT, it returns false (no ResultSet). executeUpdate() is more suitable for INSERT/UPDATE/DELETE as it returns the number of rows affected.

📖 Line-by-Line Explanation
connection
The Connection object created in Step 2 — holds the live DB session
close()
Non-static method of Connection interface. Terminates the DB session, releases all DB resources held by this connection.
System.out.println(...)
Prints confirmation message to console after successful INSERT. Runs only if no exception was thrown.
🔹 Why closing connection is critical
  • Each open connection occupies memory on both Java side and DB server side
  • Databases have a maximum connection limit — not closing connections causes connection pool exhaustion
  • Unclosed connections → memory leaks → application slowdown or crash
  • In production, connection pools (HikariCP, C3P0) manage connections — they expect connections to be returned (closed) after use
🔹 Correct Closing Order (when ResultSet and Statement also used)
rs.close(); // 1. Close ResultSet first statement.close(); // 2. Close Statement second connection.close(); // 3. Close Connection last

👉 In this program, only Connection is used (Statement not closed separately) — for complete cleanup, close Statement too.

⚠️ Better Practice — try-with-resources (Java 7+):
try (Connection connection = DriverManager.getConnection(url, user, pwd); Statement statement = connection.createStatement()) { statement.execute("insert into employee values(101,'Pravin',50000)"); } // Auto-closes connection and statement — no need to call close() manually
Using try-with-resources ensures resources are closed even if an exception occurs.
connection.close() terminates the active DB session and releases all database resources. Not closing connections causes connection pool exhaustion and memory leaks. Best practice is to use try-with-resources for automatic closure in modern Java.
