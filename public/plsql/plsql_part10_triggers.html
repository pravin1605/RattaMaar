1. What is a Trigger?
Interview Definition — One Line

A Trigger is a stored PL/SQL block that Oracle automatically executes in response to a specified database event such as INSERT, UPDATE, DELETE, CREATE, ALTER, or DROP.

  • A trigger is stored permanently in the Oracle database
  • It fires automatically — the developer does not call it manually
  • It cannot accept parameters directly
  • It is associated with a specific table, view, schema, or database event
  • Commonly used for validation, auditing, logging, security, and data integrity
User Performs Action → INSERT / UPDATE / DELETE
↓
Oracle Detects the Event
↓
Trigger Fires Automatically
↓
Trigger Logic Executes
Memory Trick

Trigger = Alarm System — you set it up once, it fires automatically whenever the event happens

Procedure = called by you  |  Trigger = called by Oracle automatically

3. Why Do We Use Triggers?
Validation Auditing Logging Security Data Integrity Automatic Calculations Maintaining History Tables Backup on Delete Preventing Invalid Operations
Extra — Real World Use Cases

Bank systems: trigger fires on every UPDATE to salary/account to log changes in an audit table.

HR systems: trigger prevents deletion of key employees like managers or presidents.

E-commerce: trigger auto-inserts a backup record every time an order is deleted.

4. General Syntax of a Trigger
TRIGGER — GENERAL SYNTAX
CREATE [OR REPLACE] TRIGGER trigger_name {BEFORE | AFTER} -- Timing: when trigger fires {INSERT | UPDATE | DELETE} -- Event: what action fires it ON table_name -- Table associated with the trigger [FOR EACH ROW] -- Row-level trigger (optional) BEGIN -- Trigger logic here END; /
KeywordMeaning
CREATE OR REPLACE TRIGGERCreate or overwrite the trigger
BEFORE / AFTERTiming — whether trigger fires before or after the event
INSERT / UPDATE / DELETEThe event that fires the trigger
ON table_nameThe table this trigger is attached to
FOR EACH ROWMakes it a Row-Level trigger — fires once per affected row
:OLDPseudo record — holds the original (old) values of the row

RAISE_APPLICATION_ERRORRaises a custom error and stops the operation
5. Types of Triggers

Triggers are classified in three ways:

Based on Event
  • DML Trigger
  • DDL Trigger
  • Database Trigger
Based on Timing
  • BEFORE Trigger
  • AFTER Trigger
Based on Level
  • Statement-Level Trigger
  • Row-Level Trigger (FOR EACH ROW)
6. Types Based on Event
Trigger TypeEventsUsed For
DML TriggerINSERT, UPDATE, DELETEValidating and controlling data changes on tables
DDL TriggerCREATE, ALTER, DROP, TRUNCATE, RENAMEAuditing schema changes — who created or dropped objects
Database TriggerLOGON, LOGOFF, STARTUP, SHUTDOWNSession tracking, welcome messages, security logging
Extra — DDL Trigger Example

A DDL Trigger on AFTER CREATE ON SCHEMA fires automatically every time a new object (table, procedure, function) is created in the schema. Used for audit trails of database changes.

7. Types Based on Timing
BEFORE Trigger
  • Fires BEFORE the DML event is applied to the table
  • Used for validation — can stop the operation before data changes
  • Used for modifying :NEW values before they are saved
  • If RAISE_APPLICATION_ERROR is called → DML is cancelled
Action → BEFORE Trigger → Data Saved
AFTER Trigger
  • Fires AFTER the DML event is applied to the table
  • Data is already changed when trigger runs
  • Used for auditing, logging, history maintenance
  • Cannot modify :NEW values — data is already written
Action → Data Saved → AFTER Trigger
8. Types Based on Level
Statement-Level Trigger
  • Executes ONCE per SQL statement
  • Regardless of how many rows are affected
  • Does NOT use FOR EACH ROW
  • Cannot access :OLD or :NEW values

Example: UPDATE EMP SET SAL = SAL+100 (100 rows) → trigger fires ONCE

Row-Level Trigger
  • Executes ONCE for EACH affected row
  • Must use FOR EACH ROW keyword
  • Can access :OLD and :NEW pseudo records
  • Most commonly used in real applications

Example: UPDATE EMP SET SAL = SAL+100 (10 rows) → trigger fires 10 TIMES

Memory Trick

No FOR EACH ROW = Statement-Level (fires once)  |  WITH FOR EACH ROW = Row-Level (fires per row)

:OLD and :NEW are only available in Row-Level triggers (FOR EACH ROW)

9. Pseudo Records — :OLD and :NEW
Definition

:OLD and :NEW are special pseudo records automatically provided by Oracle in Row-Level triggers. They hold the column values of the row before and after the DML operation.

Operation:OLD:NEW
INSERTNot available — no old data existsAvailable — holds the new values being inserted
UPDATEAvailable — holds the original valuesAvailable — holds the updated values
DELETEAvailable — holds the deleted valuesNot available — data is being removed
Extra — How to Use :OLD and :NEW

Access column values using dot notation:   :OLD.SAL   :NEW.SAL   :OLD.ENAME   :NEW.EMPNO

Example: Before update SAL = 3000, after update SAL = 5000 → :OLD.SAL = 3000, :NEW.SAL = 5000

In BEFORE triggers you can modify :NEW values. In AFTER triggers :NEW values cannot be changed.

Important — :OLD and :NEW Only in Row-Level Triggers

:OLD and :NEW are ONLY available when FOR EACH ROW is used. In Statement-Level triggers, there is no concept of individual rows — so :OLD and :NEW do not exist.

10. RAISE_APPLICATION_ERROR
Definition

RAISE_APPLICATION_ERROR is a built-in Oracle procedure used inside triggers and procedures to raise a custom user-defined error. When called, it stops the current DML operation and returns a custom error message to the user.

RAISE_APPLICATION_ERROR — SYNTAX
RAISE_APPLICATION_ERROR(error_number, error_message); -- error_number : must be between -20000 and -20999 (user-defined range) -- error_message: custom message string shown to the user -- Example: RAISE_APPLICATION_ERROR(-20001, 'SALARY MUST BE GREATER THAN OR EQUAL TO 1000');
Extra — Error Number Range

Oracle reserves error numbers -20000 to -20999 for user-defined errors. You must always use a number within this range when calling RAISE_APPLICATION_ERROR. Numbers outside this range will cause an error.

11. Trigger Examples — Validation & Security
Trigger 1 — T1: Salary Validation on INSERT (BEFORE INSERT)
Requirement: Salary must be >= 1000 when inserting a new employee. If salary is less than 1000, raise an error and stop the INSERT.
Logic: BEFORE INSERT fires before data is saved → check :NEW.SAL → if less than 1000 → RAISE_APPLICATION_ERROR → INSERT is cancelled.
T1 — SALARY VALIDATION ON INSERT
CREATE OR REPLACE TRIGGER T1 BEFORE INSERT ON EMP FOR EACH ROW BEGIN -- Check if new salary is below the minimum allowed IF :NEW.SAL < 1000 THEN RAISE_APPLICATION_ERROR(-20001, 'SALARY MUST BE GREATER THAN OR EQUAL TO 1000'); END IF; END; / -- Test: Insert with salary below 1000 INSERT INTO EMP(EMPNO, ENAME, SAL) VALUES(111, 'ROHIT', 264);
Output: ORA-20001: SALARY MUST BE GREATER THAN OR EQUAL TO 1000  → INSERT is blocked
Trigger 2 — T2: Prevent Salary Reduction on UPDATE (BEFORE UPDATE)
Requirement: New salary cannot be less than the current salary. Salary can only increase or stay the same.
Logic: BEFORE UPDATE → compare :NEW.SAL with :OLD.SAL → if new is less → RAISE_APPLICATION_ERROR → UPDATE is cancelled.
T2 — PREVENT SALARY REDUCTION ON UPDATE
CREATE OR REPLACE TRIGGER T2 BEFORE UPDATE ON EMP FOR EACH ROW BEGIN -- :OLD.SAL = current salary, :NEW.SAL = salary being set IF :NEW.SAL < :OLD.SAL THEN RAISE_APPLICATION_ERROR(-20002, 'NEW SALARY CANNOT BE LESS THAN OLD SALARY'); END IF; END; / -- Test: Try to reduce SMITH's salary from 800 to 500 UPDATE EMP SET SAL = 500 WHERE EMPNO = 7369;
Output: ORA-20002: NEW SALARY CANNOT BE LESS THAN OLD SALARY  → UPDATE is blocked
Trigger 3 — T4: Prevent Deletion of MILLER (BEFORE DELETE)
Requirement: Employee MILLER must never be deleted from the EMP table.
Logic: BEFORE DELETE → check :OLD.ENAME → if it equals 'MILLER' → RAISE_APPLICATION_ERROR → DELETE is cancelled.
T4 — PREVENT DELETION OF MILLER
CREATE OR REPLACE TRIGGER T4 BEFORE DELETE ON EMP FOR EACH ROW BEGIN -- UPPER ensures check works regardless of case IF UPPER(:OLD.ENAME) = 'MILLER' THEN RAISE_APPLICATION_ERROR(-20004, 'MILLER CANNOT BE DELETED'); END IF; END; / -- Test: Try to delete MILLER DELETE FROM EMP WHERE ENAME = 'MILLER';
Output: ORA-20004: MILLER CANNOT BE DELETED  → DELETE is blocked
12. Trigger Examples — Auditing & History
Trigger 4 — T6: Salary History Maintenance (AFTER UPDATE)
Requirement: Every time an employee's salary is updated, store the old salary, new salary, and date in a SAL_HISTORY table automatically.
Logic: AFTER UPDATE OF SAL → insert a row into SAL_HISTORY with :OLD.SAL, :NEW.SAL, and SYSDATE.
T6 — SALARY HISTORY MAINTENANCE
-- Step 1: Create the history table CREATE TABLE SAL_HISTORY ( EMPNO NUMBER, OLD_SAL NUMBER, NEW_SAL NUMBER, ACTION_DATE DATE ); -- Step 2: Create the trigger CREATE OR REPLACE TRIGGER T6 AFTER UPDATE OF SAL ON EMP FOR EACH ROW BEGIN -- Insert old and new salary details into history table INSERT INTO SAL_HISTORY(EMPNO, OLD_SAL, NEW_SAL, ACTION_DATE) VALUES(:OLD.EMPNO, :OLD.SAL, :NEW.SAL, SYSDATE); END; / -- Step 3: Test UPDATE EMP SET SAL = 4000 WHERE EMPNO = 7369; -- Step 4: Verify SELECT * FROM SAL_HISTORY;
Output in SAL_HISTORY: EMPNO=7369   OLD_SAL=800   NEW_SAL=4000   ACTION_DATE=22-JUN-26
Trigger 5 — T5: Audit Employee Insertions (AFTER INSERT)
Requirement: Every time a new employee is inserted, log the EMPNO, action type, and date in an AUDIT_EMP table automatically.
Logic: AFTER INSERT → insert :NEW.EMPNO, 'INSERT', and SYSDATE into AUDIT_EMP table.
T5 — AUDIT EMPLOYEE INSERTIONS
-- Step 1: Create the audit table CREATE TABLE AUDIT_EMP ( EMPNO NUMBER, ACTION VARCHAR2(20), ACTION_DATE DATE ); -- Step 2: Create the trigger CREATE OR REPLACE TRIGGER T5 AFTER INSERT ON EMP FOR EACH ROW BEGIN -- Log the insert action with timestamp INSERT INTO AUDIT_EMP(EMPNO, ACTION, ACTION_DATE) VALUES(:NEW.EMPNO, 'INSERT', SYSDATE); END; / -- Step 3: Test INSERT INTO EMP VALUES(9999, 'PRAVIN', 'CLERK', NULL, SYSDATE, 5000, NULL, 10); -- Step 4: Verify SELECT * FROM AUDIT_EMP;
Output in AUDIT_EMP: EMPNO=9999   ACTION=INSERT   ACTION_DATE=22-JUN-26
Trigger 6 — T7: Backup Deleted Employees (AFTER DELETE)
Requirement: Every time an employee is deleted, automatically save a copy of their data in EMP_BACKUP table before the data is permanently lost.
Logic: AFTER DELETE → use :OLD values (deleted row) → INSERT into EMP_BACKUP.
T7 — BACKUP DELETED EMPLOYEES
-- Step 1: Create the backup table CREATE TABLE EMP_BACKUP ( EMPNO NUMBER, ENAME VARCHAR2(30), SAL NUMBER, COMM NUMBER, DEPTNO NUMBER ); -- Step 2: Create the trigger CREATE OR REPLACE TRIGGER T7 AFTER DELETE ON EMP FOR EACH ROW BEGIN -- Save deleted row's data using :OLD pseudo record INSERT INTO EMP_BACKUP(EMPNO, ENAME, SAL, COMM, DEPTNO) VALUES(:OLD.EMPNO, :OLD.ENAME, :OLD.SAL, :OLD.COMM, :OLD.DEPTNO); END; / -- Step 3: Test DELETE FROM EMP WHERE EMPNO = 7369; -- Step 4: Verify SELECT * FROM EMP_BACKUP;
Output in EMP_BACKUP: EMPNO=7369   ENAME=SMITH   SAL=800   COMM=NULL   DEPTNO=20
Trigger 7 — T_SAL_AUDIT: Salary Audit with Difference (AFTER UPDATE)
Requirement: Log old salary, new salary, the difference (increase or decrease), and date every time salary is updated.
Logic: SAL_DIFF = :NEW.SAL - :OLD.SAL → positive means increase, negative means decrease.
T_SAL_AUDIT — SALARY AUDIT WITH DIFFERENCE
-- Step 1: Create audit table with salary difference column CREATE TABLE AUDIT_SAL ( EMPNO NUMBER, OLD_SAL NUMBER, NEW_SAL NUMBER, SAL_DIFF NUMBER, -- Positive = increase, Negative = decrease ACTION_DATE DATE ); -- Step 2: Create the trigger CREATE OR REPLACE TRIGGER T_SAL_AUDIT AFTER UPDATE OF SAL ON EMP FOR EACH ROW BEGIN INSERT INTO AUDIT_SAL(EMPNO, OLD_SAL, NEW_SAL, SAL_DIFF, ACTION_DATE) VALUES(:OLD.EMPNO, :OLD.SAL, :NEW.SAL, :NEW.SAL - :OLD.SAL, -- Calculate salary difference SYSDATE); END; / -- Step 3: Test UPDATE EMP SET SAL = 3500 WHERE EMPNO = 7369; -- Step 4: Verify SELECT * FROM AUDIT_SAL;
Output: EMPNO=7369   OLD_SAL=800   NEW_SAL=3500   SAL_DIFF=2700   ACTION_DATE=22-JUN-26

Extra — USER_TRIGGERS View

USER_TRIGGERS is an Oracle data dictionary view that stores information about all triggers in the current user's schema — including name, type, timing, event, table name, and current status (ENABLED / DISABLED).

Common Mistakes with Triggers

1. Using COMMIT or ROLLBACK inside a trigger → not allowed — Oracle raises an error

2. Using :OLD or :NEW without FOR EACH ROW → not available in Statement-Level triggers

3. Trying to modify :NEW values in an AFTER trigger → not allowed — data already written

4. Using error number outside -20000 to -20999 in RAISE_APPLICATION_ERROR → error

5. Forgetting UPPER() when comparing string values → 'miller' ≠ 'MILLER' → trigger fails silently

15. Frequently Asked Interview Questions
Q1. What is a trigger in PL/SQL?
A trigger is a stored PL/SQL block that Oracle automatically executes in response to a specified database event such as INSERT, UPDATE, DELETE, CREATE, ALTER, or DROP. The developer does not call it manually.
Q2. What is the difference between a stored procedure and a trigger?
A stored procedure is called explicitly by the user using EXEC. A trigger fires automatically when a database event occurs. Procedures can accept parameters; triggers cannot. COMMIT and ROLLBACK are allowed in procedures but not in triggers.
Q3. What are :OLD and :NEW in a trigger?
:OLD and :NEW are pseudo records available in Row-Level triggers. :OLD holds the column values before the DML operation. :NEW holds the column values after the DML operation. For INSERT — only :NEW is available. For DELETE — only :OLD is available. For UPDATE — both are available.
Q4. What is the difference between BEFORE and AFTER triggers?
BEFORE trigger fires before the DML event is applied — used for validation and restricting operations. AFTER trigger fires after the DML event is applied — used for auditing, logging, and history maintenance. BEFORE triggers can modify :NEW values; AFTER triggers cannot.
Q5. What is the difference between a Row-Level and Statement-Level trigger?
A Row-Level trigger uses FOR EACH ROW and fires once for every affected row. A Statement-Level trigger fires once per SQL statement regardless of how many rows are affected. Only Row-Level triggers can access :OLD and :NEW values.
Q6. Can we use COMMIT or ROLLBACK inside a trigger?
No. Oracle does not allow COMMIT or ROLLBACK inside a normal DML trigger. The trigger runs as part of the same transaction as the triggering statement. Using COMMIT or ROLLBACK inside a trigger raises an ORA-04092 error.
Q7. What is RAISE_APPLICATION_ERROR? Extra
RAISE_APPLICATION_ERROR is a built-in Oracle procedure that raises a custom user-defined error and stops the current DML operation. The error number must be between -20000 and -20999. Syntax: RAISE_APPLICATION_ERROR(-20001, 'Custom message');
Q8. Can one table have multiple triggers? Extra
Yes. Multiple triggers can exist on the same table. For example, a table can have both a BEFORE INSERT trigger for validation and an AFTER INSERT trigger for auditing. Oracle fires them in the order they were created.
Q9. What is the difference between AFTER UPDATE and AFTER UPDATE OF column? Extra
AFTER UPDATE fires for any UPDATE on the table regardless of which column is changed. AFTER UPDATE OF SAL fires only when the SAL column specifically is updated. Using OF column makes the trigger more precise and avoids unnecessary executions.
Q10. How do you view and manage triggers in Oracle? Extra
View triggers: SELECT TRIGGER_NAME, TRIGGER_TYPE, STATUS FROM USER_TRIGGERS; Disable: ALTER TRIGGER T1 DISABLE; Enable: ALTER TRIGGER T1 ENABLE; Drop: DROP TRIGGER T1; Disable all on table: ALTER TABLE EMP DISABLE ALL TRIGGERS;
