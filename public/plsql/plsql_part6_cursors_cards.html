1. What is a Cursor?
Interview Definition

A Cursor is a private SQL memory area — also called an Active Set Memory Area or Context Memory Area — which is used to process multiple records returned by a SQL query. A cursor processes data record by record, one row at a time.

  • A cursor is a pointer to a private memory area (PGA — Program Global Area) allocated by Oracle
  • It stores the result set of a SQL query temporarily in memory
  • Used whenever a SQL statement returns or affects one or more rows
  • Allows PL/SQL to process rows one at a time using FETCH
Memory Trick

Cursor = Private Memory Box where Oracle stores query results row by row

SELECT INTO = 1 row → Implicit Cursor  |  Multiple rows → Explicit Cursor

2. Types of Cursors
Implicit Cursor
  • Automatically created by Oracle
  • Used for single-row SELECT INTO and DML statements
  • Developer cannot control it
  • Always named SQL by Oracle
  • Attributes accessed as SQL%attribute
Explicit Cursor
  • Manually created and controlled by the developer
  • Used for multi-row queries
  • Developer controls DECLARE→OPEN→FETCH→CLOSE
  • Also called Active Set Memory Area
  • Named by the developer (e.g., C1)
3. Implicit Cursor — Definition & Attributes
Definition

An Implicit Cursor is automatically created and managed by Oracle whenever a SQL statement returns a single record. It is used with SELECT INTO and DML operations (INSERT, UPDATE, DELETE). Oracle always names it SQL — accessed as SQL%attribute_name.

1. SQL%FOUND

Returns TRUE if the last SQL statement affected at least one row.

Returns FALSE if no rows were affected.

Used after: SELECT INTO, UPDATE, DELETE, INSERT

2. SQL%NOTFOUND

Returns TRUE if the last SQL statement did NOT affect any row.

Returns FALSE if at least one row was affected.

Exact opposite of SQL%FOUND

3. SQL%ROWCOUNT

Returns the number of rows affected by the last DML operation.

Example: If UPDATE affects 5 rows → SQL%ROWCOUNT returns 5

4. SQL%ISOPEN

Always returns FALSE for Implicit Cursors.

Oracle automatically opens and closes them — the developer cannot keep them open.

AttributeReturnsTRUE WhenFALSE When
SQL%FOUNDBOOLEANAt least one row was affectedNo rows were affected
SQL%NOTFOUNDBOOLEANNo rows were affectedAt least one row was affected
SQL%ROWCOUNTNUMBERReturns count of rows affectedReturns 0 if no rows affected

Extra — Important Rule

SQL%FOUND and SQL%NOTFOUND are always exact opposites. SQL%ISOPEN is always FALSE for Implicit Cursors. Always check SQL%FOUND or SQL%ROWCOUNT BEFORE calling ROLLBACK — ROLLBACK resets the cursor state.

4. Implicit Cursor — Program Examples
Example 1 — SQL%FOUND with UPDATE (DEPTNO 10)
Task: Update salary of all employees in DEPTNO 10 by +100. Check if update was successful using SQL%FOUND.
Logic: CLARK, KING, MILLER are in DEPTNO 10 → 3 rows affected → SQL%FOUND = TRUE → IF block executes.
SQL%FOUND — UPDATE DEPTNO 10
BEGIN -- Update salary of DEPTNO 10 employees by 100 UPDATE EMP SET SAL = SAL + 100 WHERE DEPTNO = 10; -- Check if any rows were updated IF SQL%FOUND THEN DBMS_OUTPUT.PUT_LINE('RECORD UPDATED'); ELSE DBMS_OUTPUT.PUT_LINE('RECORD NOT UPDATED'); END IF; END; /
Output: RECORD UPDATED  → CLARK, KING, MILLER salaries increased by 100
Example 2 — SQL%FOUND after ROLLBACK
Task: Same UPDATE on DEPTNO 10, but ROLLBACK is called before checking SQL%FOUND.
Logic: ROLLBACK is itself a SQL statement. After it executes, SQL%FOUND checks ROLLBACK's result — which affects no data rows → SQL%FOUND = FALSE → ELSE block runs.
SQL%FOUND — AFTER ROLLBACK
BEGIN -- Update salary of DEPTNO 10 employees UPDATE EMP SET SAL = SAL + 100 WHERE DEPTNO = 10; -- Rollback undoes the update ROLLBACK; -- SQL%FOUND now reflects ROLLBACK's result (no data affected) IF SQL%FOUND THEN DBMS_OUTPUT.PUT_LINE('RECORD UPDATED'); ELSE DBMS_OUTPUT.PUT_LINE('RECORD NOT UPDATED'); END IF; END; /
Output: RECORD NOT UPDATED  → ROLLBACK reset the DML state
Example 3 — SQL%FOUND with DELETE (EMPNO 7934)
Task: Delete MILLER (EMPNO 7934). Check if deletion was successful using SQL%FOUND.
Logic: MILLER exists → DELETE affects 1 row → SQL%FOUND = TRUE → IF block executes.
SQL%FOUND — DELETE
BEGIN -- Delete MILLER from EMP table DELETE FROM EMP WHERE EMPNO = 7934; -- Check if deletion was successful IF SQL%FOUND THEN DBMS_OUTPUT.PUT_LINE('RECORD DELETED'); ELSE DBMS_OUTPUT.PUT_LINE('RECORD NOT FOUND'); END IF; END; /
Output: RECORD DELETED  → EMPNO 7934 (MILLER) found and deleted
Example 4 — SQL%FOUND with INSERT
Task: Insert a new employee PRAVIN (EMPNO 101). Check if insertion was successful using SQL%FOUND.
Logic: INSERT always affects exactly 1 row when it succeeds → SQL%FOUND = TRUE → IF block executes.
SQL%FOUND — INSERT
BEGIN -- Insert a new employee record INSERT INTO EMP(EMPNO, ENAME) VALUES(101, 'PRAVIN'); -- Check if insertion was successful IF SQL%FOUND THEN DBMS_OUTPUT.PUT_LINE('RECORD INSERTED'); ELSE DBMS_OUTPUT.PUT_LINE('RECORD NOT INSERTED'); END IF; END; /
Output: RECORD INSERTED  → INSERT always affects 1 row on success
Example 5 — SQL%NOTFOUND with UPDATE (DEPTNO 10)
Task: Update salary of DEPTNO 10. Check using SQL%NOTFOUND (opposite of %FOUND).
Logic: Rows exist → UPDATE affects rows → SQL%NOTFOUND = FALSE → ELSE block runs (RECORD UPDATED is printed).
SQL%NOTFOUND — UPDATE DEPTNO 10
BEGIN -- Update salary of DEPTNO 10 employees UPDATE EMP SET SAL = SAL + 100 WHERE DEPTNO = 10; -- SQL%NOTFOUND = FALSE (rows were updated) → ELSE block runs IF SQL%NOTFOUND THEN DBMS_OUTPUT.PUT_LINE('RECORD NOT UPDATED'); ELSE DBMS_OUTPUT.PUT_LINE('RECORD UPDATED'); END IF; END; /
Output: RECORD UPDATED  → SQL%NOTFOUND = FALSE → ELSE block executes
Example 6 — SQL%ROWCOUNT with UPDATE (DEPTNO 20)
Task: Update salary of DEPTNO 20 by +10. Display how many rows were affected using SQL%ROWCOUNT.
Logic: DEPTNO 20 has SMITH, JONES, SCOTT, ADAMS, FORD = 5 employees → SQL%ROWCOUNT = 5.
SQL%ROWCOUNT — UPDATE DEPTNO 20
BEGIN -- Update salary of all DEPTNO 20 employees by 10 UPDATE EMP SET SAL = SAL + 10 WHERE DEPTNO = 20; -- Display how many rows were affected DBMS_OUTPUT.PUT_LINE(SQL%ROWCOUNT || ' RECORDS WERE AFFECTED'); END; /
Output: 5 RECORDS WERE AFFECTED  → SMITH, JONES, SCOTT, ADAMS, FORD are in DEPTNO 20
5. Explicit Cursor — Definition & Lifecycle
Definition

An Explicit Cursor is a cursor that is manually defined and controlled by the developer. It is used when a SQL statement returns multiple records. The developer explicitly controls every step: DECLARE, OPEN, FETCH, and CLOSE. It is also called an Active Set Memory Area.

1
DECLARE
Define cursor with SELECT in DECLARE section. Only structure created — no data yet.
2
OPEN
Execute SELECT query. Oracle loads all matching rows into cursor memory. Pointer placed before row 1.
3
FETCH
Retrieve one row at a time from cursor memory into PL/SQL variables. Use LOOP to fetch all rows.
4
CLOSE
Release all PGA memory allocated for the cursor. Always CLOSE after use.
Memory Trick

D-O-F-C → DECLARE → OPEN → FETCH → CLOSE  |  "Don't Open Files Carelessly"

Extra — %ISOPEN: Implicit vs Explicit

Implicit Cursor: SQL%ISOPEN = ALWAYS FALSE — Oracle auto-manages it.

Explicit Cursor: C1%ISOPEN = TRUE while cursor is open (between OPEN and CLOSE), FALSE otherwise.

7. Explicit Cursor — Program Examples
Example 1 — Fetch Only the First Row (Single FETCH, No Loop)
Task: Open cursor C1 on EMP table and fetch only the first row — no loop used.
Logic: Single FETCH retrieves only the first row (SMITH 800). Remaining 13 rows stay in cursor memory but are never fetched.
EXPLICIT CURSOR — SINGLE FETCH
DECLARE V_NAME VARCHAR2(20); V_SAL NUMBER; -- Define cursor with SELECT query CURSOR C1 IS SELECT ENAME, SAL FROM EMP; BEGIN OPEN C1; -- Execute query, load rows FETCH C1 INTO V_NAME, V_SAL; -- Fetch only first row DBMS_OUTPUT.PUT_LINE(V_NAME || ' ' || V_SAL); CLOSE C1; -- Release memory END; /
Output: SMITH 800  → Only first row fetched — a single FETCH retrieves one row only
Example 2 — Fetch All Rows Using SIMPLE LOOP + EXIT WHEN %NOTFOUND
Task: Fetch and display name and salary of all 14 employees from EMP table.
Logic: LOOP → FETCH one row → EXIT WHEN C1%NOTFOUND (stops when no more rows) → display → repeat.
EXPLICIT CURSOR — FETCH ALL ROWS
DECLARE V_NAME VARCHAR2(20); V_SAL NUMBER; -- Define cursor to fetch all employees CURSOR C1 IS SELECT ENAME, SAL FROM EMP; BEGIN OPEN C1; -- Load all rows into cursor memory LOOP FETCH C1 INTO V_NAME, V_SAL; -- Fetch one row at a time EXIT WHEN C1%NOTFOUND; -- Exit when no more rows remain DBMS_OUTPUT.PUT_LINE(V_NAME || ' ' || V_SAL); END LOOP; CLOSE C1; -- Release cursor memory END; /
Output: SMITH 800 → ALLEN 1600 → WARD 1250 → JONES 2975 → ... → MILLER 1300  (all 14 rows)
Example 3 — Fetch Only Employees with SAL > 2000 Using WHERE in Cursor
Task: Fetch names and salaries of employees whose salary is greater than 2000.
Logic: WHERE SAL > 2000 filters at cursor level — only 6 employees qualify: JONES, BLAKE, CLARK, SCOTT, KING, FORD.
EXPLICIT CURSOR — FILTERED FETCH (SAL > 2000)
DECLARE V_NAME VARCHAR2(20); V_SAL NUMBER; -- Define cursor with WHERE filter CURSOR C1 IS SELECT ENAME, SAL FROM EMP WHERE SAL > 2000; BEGIN OPEN C1; -- Only 6 matching rows loaded LOOP FETCH C1 INTO V_NAME, V_SAL; -- Fetch one row at a time EXIT WHEN C1%NOTFOUND; -- Exit when no more rows remain DBMS_OUTPUT.PUT_LINE(V_NAME || ' ' || V_SAL); END LOOP; CLOSE C1; -- Release cursor memory END; /
Output: JONES 2975   BLAKE 2850   CLARK 2450   SCOTT 3000   KING 5000   FORD 3000

Common Mistakes with Cursors

1. Forgetting EXIT WHEN cursor%NOTFOUND → loop runs forever after last row

2. Placing EXIT WHEN before FETCH → last row is always skipped and never displayed

3. Forgetting CLOSE cursor → memory not released — causes memory leak

4. Using Explicit Cursor for a single row → use SELECT INTO instead

5. FETCH without OPEN → ORA-01001: Invalid Cursor error

10. Frequently Asked Interview Questions
Q1. What is a cursor in PL/SQL?
A cursor is a private SQL memory area (also called a Context Memory Area or Active Set Memory Area) used to process SQL query results. It processes data record by record, one row at a time.
Q2. What are the types of cursors in PL/SQL?
1. Implicit Cursor — automatically created by Oracle for single-row SELECT INTO and DML statements.   2. Explicit Cursor — manually defined and controlled by the developer for multi-row queries.
Q3. What is the lifecycle of an Explicit Cursor?
DECLARE → OPEN → FETCH → CLOSE. Memory tip: D-O-F-C — "Don't Open Files Carelessly". Only BEGIN and CLOSE are mandatory after DECLARE.
Q4. What are the Implicit Cursor attributes?
SQL%FOUND (TRUE if rows affected), SQL%NOTFOUND (TRUE if no rows affected), SQL%ROWCOUNT (number of rows affected), SQL%ISOPEN (always FALSE for implicit cursors).
Q5. What is the difference between Implicit and Explicit Cursors?
Implicit Cursor is auto-created by Oracle for single-row operations — developer cannot control it. Explicit Cursor is manually created by the developer for multi-row queries — developer fully controls DECLARE, OPEN, FETCH, and CLOSE.
Q6. Why is EXIT WHEN placed after FETCH and not before? Extra
If EXIT WHEN is placed before FETCH, it checks the result of the previous iteration's FETCH — meaning the last row is always skipped. Placing it after FETCH ensures every fetched row is processed before checking if the cursor is exhausted.
Q7. What happens if we do not CLOSE a cursor? Extra
PGA memory allocated to the cursor is not released — causing a memory leak. In large applications, unclosed cursors can cause ORA-01000: maximum open cursors exceeded error.
Q8. What is SQL%ROWCOUNT and when is it used? Extra
SQL%ROWCOUNT returns the number of rows affected by the last DML operation. Example: UPDATE EMP SET SAL = SAL+10 WHERE DEPTNO = 20 → SQL%ROWCOUNT returns 5 because DEPTNO 20 has 5 employees.
Q9. What is the difference between %ISOPEN for Implicit and Explicit Cursors? Extra
For Implicit Cursors: SQL%ISOPEN is always FALSE — Oracle auto-manages them. For Explicit Cursors: C1%ISOPEN returns TRUE when cursor is open (between OPEN and CLOSE) and FALSE otherwise.
