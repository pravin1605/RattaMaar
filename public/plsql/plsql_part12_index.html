SQL — Indexes in Oracle

1. What is an Index?
Interview Definition — One Line

An Index is a database object that stores column values and ROWIDs to speed up data retrieval operations by reducing full table scans on large tables.

  • Works like the index of a book — instead of reading every page, you jump directly to the required page
  • Oracle uses indexes to quickly locate rows without scanning the entire table
  • Stored as a separate database object — independent of the table
  • Automatically maintained by Oracle when DML (INSERT, UPDATE, DELETE) occurs
  • Can be created on one column (Single) or multiple columns (Composite)
Without Index: Full Table Scan → check every row → slow for large tables
With Index: Search index → get ROWID → jump directly to the row → fast
Memory Trick

Index = Book's index page — instead of reading all 1000 pages to find "Database", the index says "Database → Page 450" and you go directly there

ROWID = Physical address of a row in Oracle — like a GPS coordinate for the exact row location

2. How Index Works Internally

Oracle stores the index as a separate structure containing the indexed column value paired with the ROWID of each matching row.

Index Structure (Simplified)

EMPNO    ROWID
101   → AA123
102   → AA124
103   → AA125

Query Execution with Index
  • Step 1: Oracle searches the index for EMPNO = 102
  • Step 2: Gets ROWID = AA124
  • Step 3: Directly fetches that row from the table
Extra — What is ROWID?

ROWID is the physical address of a row inside Oracle's storage. It uniquely identifies each row's exact location on disk (file number, block number, row number within the block). Oracle uses ROWID to directly fetch a row without scanning other rows.

Example: SELECT ROWID, EMPNO, ENAME FROM EMP; → shows each row's physical address.

3. B-Tree Index Structure (Oracle Default)

Most Oracle indexes use a B-Tree (Balanced Tree) structure with three levels:

ROOT | ------------------------- | | BRANCH BRANCH | | ----------- ------------- | | | | | | LEAF LEAF LEAF LEAF LEAF LEAF Each LEAF contains: Index Value + ROWID
LevelNameContains
TopRoot BlockEntry point — pointers to Branch blocks
MiddleBranch BlockIntermediate — pointers to Leaf blocks
BottomLeaf BlockActual data — Index Value + ROWID pairs
Extra — Why Balanced Tree?

B-Tree is "balanced" — every leaf is at the same depth from the root. This means every search takes the same number of steps regardless of which value you search for. Oracle can find any value in O(log n) time instead of O(n) for full table scan.

4. Advantages and Disadvantages of Indexes
Advantages
  • Faster query execution — WHERE clause searches
  • Reduces disk I/O — fewer blocks read
  • Improves JOIN performance
  • Improves ORDER BY and GROUP BY performance
  • Automatically used by Oracle's query optimizer
Disadvantages
  • Extra storage space required for index structure
  • INSERT is slower — table AND index both updated
  • UPDATE is slower — index must be updated
  • DELETE is slower — entries removed from both table and index
  • Over-indexing can hurt DML performance
Important — Index Does NOT Help All Queries

Index helps: WHERE col = value, WHERE col > value, JOIN on indexed col, ORDER BY indexed col.

Index may NOT help: queries returning most rows (full scan is faster), functions on indexed column without function-based index, OR conditions on non-indexed columns.

Extra — Oracle Clustered Index Note

Oracle does not use SQL Server-style Clustered Indexes. Oracle's equivalent is an "Index Organized Table (IOT)" where table data is stored in B-Tree index order. A normal CREATE INDEX in Oracle always creates a Non-Clustered B-Tree index.

7. Types of Non-Clustered Indexes — Detailed
1. Single Column Index

Created on a single column. Most basic and commonly used type of index.

Best used on columns frequently used in WHERE clauses with high cardinality (many distinct values).

SINGLE COLUMN INDEX
-- Create index on SAL column CREATE INDEX IDX_SAL ON EMP(SAL); -- This query now uses the index SELECT * FROM EMP WHERE SAL = 5000;
Index IDX_SAL used → Oracle jumps directly to rows with SAL = 5000
2. Composite Index (Multi-Column Index)

Created on two or more columns together. Column order in the index matters — the first column listed is the leading column.

Most effective when all indexed columns are used in WHERE clause. Less effective when only a non-leading column is used alone.

COMPOSITE INDEX (MULTI-COLUMN)
-- Create composite index on ENAME and DEPTNO CREATE INDEX IDX_ENAME_DNO ON EMP(ENAME, DEPTNO); -- Best: both columns used → full index scan SELECT * FROM EMP WHERE ENAME = 'SMITH' AND DEPTNO = 10; -- Also works: leading column used → partial index scan SELECT * FROM EMP WHERE ENAME = 'SMITH'; -- Less effective: only non-leading column → may skip index SELECT * FROM EMP WHERE DEPTNO = 10;
Best performance when ENAME (leading column) is included in WHERE clause
3. Unique Index

Ensures all values in the indexed column are unique. No two rows can have the same value for the indexed column.

Oracle automatically creates a Unique Index when you add a PRIMARY KEY or UNIQUE constraint to a column.

UNIQUE INDEX — PREVENT DUPLICATE VALUES
-- Create table CREATE TABLE CUST ( CID NUMBER, CNAME VARCHAR2(20), ADDRESS VARCHAR2(50) ); -- Create unique index on CID CREATE UNIQUE INDEX IDX_CUST_ID ON CUST(CID); -- Insert valid rows INSERT INTO CUST VALUES(1, 'AMIT', 'BANGALORE'); INSERT INTO CUST VALUES(2, 'RAHUL', 'PUNE'); -- Try to insert duplicate CID = 1 INSERT INTO CUST VALUES(1, 'SURESH', 'MUMBAI');
Error: ORA-00001: Unique Constraint Violated → CID = 1 already exists
4. Reverse Key Index

Stores the bytes of each index value in reverse order. Used to prevent "hot blocks" — when sequence-generated IDs cause all INSERTs to go to the same index block.

Normal: 1001, 1002, 1003, 1004 → all stored at same end of index → contention

Reverse: 1001→1001, 1002→2001, 1003→3001, 1004→4001 → values spread across index blocks → less contention

REVERSE KEY INDEX
-- Create reverse key index on EMPNO CREATE INDEX IDX_EMP_REV ON EMP(EMPNO) REVERSE; -- Best used when EMPNO is generated by a sequence -- Values: 1001, 1002, 1003 get distributed across blocks
Reverse Key distributes sequential values across different index blocks → reduces hot block contention
Important Limitation

Reverse Key Indexes do NOT support range queries (BETWEEN, >, <). Because the reversed values are no longer in sequential order, Oracle cannot use the index for range searches efficiently.

5. Bitmap Index

Stores index data as bitmaps (sequences of 0s and 1s). Best for columns with low cardinality — meaning very few distinct values.

For each distinct value, Oracle maintains a bit vector (bitmap) — one bit per row. 1 = row has this value, 0 = row does not.

Best For (Low Cardinality)
  • GENDER (M / F)
  • STATUS (ACTIVE / INACTIVE)
  • MARITAL STATUS (Y / N)
  • DEPT TYPE (IT / HR / SALES)
NOT For (High Cardinality)
  • EMPNO (unique per row)
  • ENAME (many distinct names)
  • SAL (many distinct values)
  • EMAIL (unique per person)
BITMAP INDEX — GENDER COLUMN
-- Create bitmap index on GENDER column CREATE BITMAP INDEX IDX_GENDER ON EMP(GENDER); -- Bitmap internally: -- GENDER M → 1 0 1 0 1 1 0 1 (1 = row is Male) -- GENDER F → 0 1 0 1 0 0 1 0 (1 = row is Female) -- Very fast for this query SELECT * FROM EMP WHERE GENDER = 'M';
Bitmap Index instantly identifies all rows where GENDER = 'M' using bit operations
6. Function-Based Index

Created on a function or expression rather than a plain column. When a query applies a function to a column in the WHERE clause, a normal index on that column is NOT used. A Function-Based Index solves this.

FUNCTION-BASED INDEX — UPPER(ENAME)
-- Problem: normal index on ENAME is NOT used here SELECT * FROM EMP WHERE UPPER(ENAME) = 'SCOTT'; -- Oracle cannot use IDX_ENAME because UPPER() is applied -- Solution: create a function-based index CREATE INDEX IDX_UPPER_NAME ON EMP(UPPER(ENAME)); -- Now this query uses the function-based index SELECT * FROM EMP WHERE UPPER(ENAME) = 'SCOTT';
IDX_UPPER_NAME is now used → fast case-insensitive search on ENAME
Extra — Other Function-Based Index Examples

CREATE INDEX IDX_LOWER ON EMP(LOWER(ENAME)); → for LOWER() queries

CREATE INDEX IDX_SAL_TAX ON EMP(SAL * 0.1); → for calculated value queries

CREATE INDEX IDX_TRUNC ON EMP(TRUNC(HIREDATE)); → for date-truncated queries

8. View Indexes
VIEW, DROP, REBUILD INDEXES
-- View all indexes in your schema SELECT INDEX_NAME, TABLE_NAME FROM USER_INDEXES; -- View indexes of a specific table SELECT INDEX_NAME, TABLE_NAME FROM USER_INDEXES WHERE TABLE_NAME = 'EMP'; -- View which columns are indexed SELECT INDEX_NAME, COLUMN_NAME FROM USER_IND_COLUMNS WHERE TABLE_NAME = 'EMP'; -- Drop an index permanently DROP INDEX IDX_SAL; -- Rebuild a fragmented index ALTER INDEX IDX_SAL REBUILD; -- Monitor index usage ALTER INDEX IDX_SAL MONITORING USAGE; SELECT * FROM V$OBJECT_USAGE; -- Check if index is being used by queries
Extra — When to Rebuild an Index?

Over time, after many INSERTs, UPDATEs, and DELETEs, an index can become fragmented — wasting space and reducing performance. ALTER INDEX ... REBUILD recreates the index from scratch in an optimized structure. It is recommended to rebuild when the index has many deleted entries or has grown significantly in size.

Extra — Foreign Key and Index

Oracle does NOT automatically create an index on a Foreign Key column. However, it is best practice to manually create an index on foreign key columns — because JOIN queries between parent and child tables frequently filter on the FK column. Without an index, Oracle performs a full table scan on the child table for each parent row.

10. When to Use and When NOT to Use an Index Extra
Use Index When
  • Column is frequently used in WHERE clause
  • Column has high cardinality (many distinct values)
  • Table is large (thousands or millions of rows)
  • Column used in JOINs (especially FK columns)
  • Column used in ORDER BY or GROUP BY
  • Queries return a small percentage of rows
Avoid Index When
  • Table is small (few rows — full scan is faster)
  • Column has low cardinality (few distinct values — use Bitmap instead)
  • Column is rarely used in WHERE clause
  • Table has heavy INSERT/UPDATE/DELETE operations
  • Query returns most rows of the table
  • Column values change frequently

Common Mistakes with Indexes

1. Creating index on every column → slows all DML operations — index only columns used in WHERE / JOIN / ORDER BY

2. Using function on indexed column without function-based index → Oracle skips the index

3. Using Bitmap Index on high-cardinality column (like EMPNO) → very inefficient — use B-Tree instead

4. Not indexing Foreign Key columns → causes full table scan on child table during JOINs

5. Expecting index on small tables to help → full table scan is often faster for small tables

12. Frequently Asked Interview Questions
Q1. What is an index in Oracle?
An index is a database object that stores column values and ROWIDs to speed up data retrieval. It works like a book's index — instead of reading every row (full table scan), Oracle jumps directly to the required rows using the index.
Q2. Does an index improve INSERT performance?
No. An index slows INSERT, UPDATE, and DELETE operations because Oracle must update both the table and all associated indexes whenever data changes. Index improves only SELECT (read) performance.
Q3. Which queries benefit most from indexes?
Queries using WHERE clause (equality and range), JOIN on indexed columns, ORDER BY on indexed column, and GROUP BY on indexed column benefit most from indexes.
Q4. What is ROWID in Oracle?
ROWID is the physical address of a row inside Oracle's storage. It uniquely identifies the exact disk location of a row (file, block, row within block). Oracle indexes store ROWID alongside the indexed value to directly fetch the matching row.
Q5. Which indexes are created automatically?
Oracle automatically creates a Unique Index when a PRIMARY KEY or UNIQUE constraint is defined on a column. Foreign Key, CHECK, and NOT NULL constraints do NOT create indexes automatically.
Q6. What is the default index type in Oracle?
B-Tree (Balanced Tree) Non-Clustered Index is the default index type in Oracle. Every CREATE INDEX statement in Oracle creates a B-Tree Non-Clustered index unless otherwise specified (BITMAP or REVERSE keywords).
Q7. What is cardinality and how does it affect index choice? Extra
Cardinality is the number of distinct values in a column. High cardinality (many distinct values, like EMPNO) → use B-Tree Index. Low cardinality (few distinct values, like GENDER with M/F) → use Bitmap Index. Using the wrong index type for the cardinality wastes space and hurts performance.
Q8. Why does a Bitmap Index NOT suit high-cardinality columns? Extra
Bitmap Index stores one bitmap (bit vector) per distinct value. For high-cardinality columns like EMPNO (thousands of unique values), it would need thousands of bitmaps — each nearly the size of the table. This wastes enormous space and makes DML operations very slow due to locking entire bitmaps.
Q9. What is a Function-Based Index and when is it used? Extra
A Function-Based Index is created on an expression or function applied to a column. When a query applies UPPER(), LOWER(), TRUNC(), or any function to a column in WHERE clause, a normal index is skipped. A Function-Based Index on the same expression allows Oracle to use the index for such queries.
Q10. What is a Composite Index and what is the leading column rule? Extra
A Composite Index is created on multiple columns together. The first column listed is the leading column. Oracle can use the index when the WHERE clause includes the leading column — either alone or with other indexed columns. If only non-leading columns are used in WHERE, Oracle may skip the index entirely.
