1. What is a Web Application, Web Service, and REST API?

These three terms are connected. Think about a food delivery application:

USER ↓ Web Application ↓ REST API ↓ Web Service ↓ Database

Important: Web Application, Web Service, and REST API are not exactly the same thing.

A. Web Application

A software application that users access through a web browser or another web client — e.g. Amazon, Facebook, Gmail, a Society Management System, a Banking Website. The user interacts through a frontend/UI.

User ↓ Browser ↓ React Frontend ↓ Spring Boot Backend ↓ Database
🍽️ Restaurant Analogy
The customer sees the visible part of a restaurant — tables, menu, waiter, food, billing counter. Similarly, the user interacts with the Web Application UI: login, click buttons, fill forms, search, view data, submit payments, download reports.

SocietyHub Example

User opens http://localhost:5173, sees Dashboard → Residents / Maintenance / Complaints / Visitors / Notices. Clicking Residents requires data — but React doesn't talk to the database directly:

React ↓ Spring Boot API ↓ Database

The web application is the complete system the user interacts with.

B. Web Service

When React needs data, it asks Spring Boot: "give me all residents." Spring Boot provides a service through which React communicates with it — that's a Web Service: a mechanism allowing different applications to communicate over a network.

Application A ↓ Internet ↓ Application B
🏦 Bank Analogy
Amazon doesn't have access to the bank's internal database. It asks the Bank API/Web Service: "Was payment transaction 123 successful?" The bank responds {"status": "SUCCESS"}. That communication is a web service.

C. REST API

A way of designing web APIs so applications communicate using standard HTTP methods and resource-based URLs. REST = Representational State Transfer.

Interview-friendly definition:
"A REST API is an API that follows REST principles and uses HTTP methods such as GET, POST, PUT, PATCH and DELETE to perform operations on resources."

GET — Read Data

Retrieves/reads data from the server. Nothing is created or deleted.

GET /api/residents
[
  { "id": 101, "name": "Rahul", "flat": "A-101" },
  { "id": 102, "name": "Amit",  "flat": "A-102" }
]
@GetMapping("/residents")
public List<Resident> getResidents() {
    return residentService.getAllResidents();
}
Real-life
Opening "Transaction History" in a bank app → app asks server "Give me my transactions" → a GET request. In SocietyHub: Chairman opens Residents page → GET /api/residents → backend returns all residents.

POST — Create Data

Generally used to create a new resource.

POST /api/residents { "name": "Rohit", "flat": "C-201", "mobile": "9876543210" }
@PostMapping("/residents")
public Resident createResident(
        @RequestBody ResidentRequest request) {
    return residentService.createResident(request);
}
Real-life
Online shopping app → "Add a new address" → provide Name, Address, City, Pincode → frontend sends info to server → new address created. That's POST.

PUT — Update / Replace Data (Whole Resource)

Resident 101 currently: Name: Rahul, Flat: A-101, Mobile: 9876543210, Occupation: Engineer. Rahul updates his info — send the full updated representation:

PUT /api/residents/101 { "name": "Rahul Patil", "flat": "A-101", "mobile": "9999999999", "occupation": "Software Engineer" }
@PutMapping("/residents/{id}")
public Resident updateResident(
        @PathVariable Long id,
        @RequestBody ResidentRequest request) {
    return residentService.updateResident(id, request);
}

PATCH — Partial Update

Updates only part of an existing resource. Rahul only changes his mobile number — no need to send everything:

PATCH /api/residents/101 { "mobile": "9999999999" }

PUT vs PATCH ⭐ (Very Common Interview Question)

PUT → Complete resource update / replacement PATCH → Partial resource update
Real-life
College student record (Name, Roll No, Mobile, Email, Address, Department): changing your complete profile → PUT. Changing only mobile number → PATCH.

DELETE — Delete Data

Used to remove a resource.

DELETE /api/residents/101
@DeleteMapping("/residents/{id}")
public void deleteResident(
        @PathVariable Long id) {
    residentService.deleteResident(id);
}

4. ⭐ Interview Answer Templates

Q: What is a Web Application?
"A web application is a software application that is accessed through a web browser or web client over a network. It generally consists of a frontend, backend and database. For example, in my SocietyHub project, React acts as the frontend, Spring Boot acts as the backend, and the database stores the application data."
Q: What is a Web Service?
"A web service is a mechanism that allows different applications to communicate with each other over a network. For example, my React frontend communicates with the Spring Boot backend through HTTP-based services to fetch or modify resident information."
Q: What is REST API?
"REST API is an API designed according to REST principles. It represents data as resources and uses HTTP methods such as GET, POST, PUT, PATCH and DELETE to perform operations on those resources. For example, GET /api/residents retrieves residents, POST /api/residents creates a resident, and DELETE /api/residents/101 deletes a particular resident."
Q: Explain HTTP Methods
"HTTP methods define what operation the client wants to perform on a resource. GET is used to retrieve data, POST is used to create a new resource, PUT is generally used for a complete update or replacement, PATCH is used for a partial update, and DELETE is used to remove a resource." Then add: "For example, in my SocietyHub project, I can use GET /api/residents to fetch residents, POST /api/residents to create a resident, PUT /api/residents/101 to update the complete resident information, PATCH /api/residents/101 to update only a particular field such as mobile number, and DELETE /api/residents/101 to delete the resident."

Why this works: You're not just giving textbook definitions — you're connecting every concept to a real project (SocietyHub), which is exactly what interviewers want to hear.

5. Interview Q&A Bank Added

Q: Is REST API the same as Web Service?
No. Web Service is the broader concept (any mechanism for inter-application communication — includes SOAP, REST, gRPC). REST API is one specific architectural style of implementing a web service using HTTP verbs and resource URLs.
Q: Why is PUT called idempotent but POST is not?
Calling PUT multiple times with the same data results in the same final state (replacing the resource each time). Calling POST multiple times typically creates multiple new resources — so it's not idempotent.
Q: What HTTP status codes are typically returned for each method?
GET → 200 OK. POST → 201 Created. PUT → 200 OK (or 204 No Content). PATCH → 200 OK. DELETE → 204 No Content (or 200 OK).
Q: Can PUT be used instead of PATCH?
Technically yes, by sending the full resource with only one field changed — but that's inefficient and not semantically correct. PATCH exists specifically to avoid resending unchanged data.
Q: What does "resource-based URL" mean in REST?
URLs represent nouns (resources), not actions — e.g. /api/residents/101, not /api/getResident?id=101. The HTTP method (verb) expresses the action, not the URL.
Q: What are the 6 REST architectural constraints?
Client-Server separation, Statelessness, Cacheability, Uniform Interface, Layered System, and (optionally) Code on Demand.
Q: What is statelessness in REST?
Each request from client to server must contain all information needed to understand and process it — the server doesn't store client session state between requests.

6. Memory Tricks Added

🧠 CRUD ↔ HTTP Mnemonic
"Create-Read-Update-Delete" maps directly to "POST-GET-PUT/PATCH-DELETE". Remember it as: "Post to Get, Put/Patch, then Delete."
🧠 PUT vs PATCH
PUT = "Put the whole thing back" (full replace). PATCH = "Patch just the hole" (partial fix). Both start differently but PUT is the bigger word action = bigger update.
🧠 Web App vs Web Service vs REST API
Web Application = the restaurant (whole experience). Web Service = the waiter (communication channel). REST API = the waiter following a specific ordering rulebook (HTTP verbs + menu/resource format).
🧠 Layered flow order
"Controllers Serve Soup, then Repositories Hand it to the Database" → Controller → Service → ServiceImpl → Repository → Hibernate → Database.

7. Common Bugs / Gotchas Added

⚠️ Using POST for updates
Beginners often use POST for every write operation. This breaks REST semantics — POST should only create new resources; use PUT/PATCH for updates.
⚠️ Forgetting @RequestBody
Without @RequestBody on POST/PUT/PATCH methods, Spring Boot won't deserialize the incoming JSON into the request object — you'll get null fields or a 400 error.
⚠️ Sending full object on PATCH
Defeats the purpose of PATCH. If you always send the whole resource, you should be using PUT instead, and your update logic (partial-field merging) becomes unnecessary complexity.
⚠️ Missing @PathVariable id mismatch
If the URL path {id} doesn't match the field name in the method signature (@PathVariable Long id), Spring throws a runtime binding error — always keep names consistent or use @PathVariable("id") explicitly.
