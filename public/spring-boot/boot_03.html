1. @EnableAutoConfiguration (Recap)

We already saw that @SpringBootApplication contains @Configuration, @EnableAutoConfiguration, @ComponentScan.

Simple Meaning

@EnableAutoConfiguration tells Spring Boot: "Automatically configure the application based on the dependencies and configuration present in the project."

If you add spring-boot-starter-web, Spring Boot understands you're building a web application and automatically configures much of the required web infrastructure. If you add spring-boot-starter-data-jpa, Spring Boot can automatically configure many JPA-related components based on your configuration.

Without Auto Configuration

Traditionally, developers had to configure many things manually: Web configuration, Database configuration, JPA configuration, Transaction configuration, JSON configuration, Server configuration.

Dependencies ↓ Spring Boot detects them ↓ Auto Configuration ↓ Required infrastructure configured
💻 New Laptop Analogy
Without automatic setup: Install OS → Install drivers → Configure network → Configure display → Configure audio → Configure keyboard... With automatic setup, much of this happens automatically based on the hardware. Similarly: Spring Boot → Looks at dependencies → Configures appropriate infrastructure.
Interview answer
"@EnableAutoConfiguration enables Spring Boot's automatic configuration mechanism. It configures the application based on the dependencies available in the classpath and the application's configuration."

2. @Service

Used to mark a class as a service/business-logic component managed by Spring.

@Service
public class ResidentServiceImpl {

    public Resident createResident(Resident resident) {
        // business logic
        return resident;
    }
}

Spring detects this class and creates a Spring Bean for it.

Why do we need @Service?

Suppose Chairman wants to create a resident. There might be business rules:

Check society ↓ Check whether email already exists ↓ Check flat number ↓ Create user ↓ Create resident profile ↓ Save data

This is business logic. We should not put all this logic inside the controller. Instead:

Controller ↓ Service ↓ Repository
🏦 Bank Analogy
Customer → Bank Counter → Bank Officer → Bank Database. The counter receives the request. The bank officer performs the actual business operation. Similarly: Controller → Service → Repository.
Interview answer
"@Service is a specialization of @Component used to mark a class as a service layer component. It is generally used to contain business logic and is managed by the Spring IoC container."

3. @Repository

Used to indicate the data-access/persistence layer.

@Repository
public interface ResidentRepository
        extends JpaRepository<Resident, Long> {
}

Its responsibility is mainly interaction with the database through Spring Data/JPA.

Architecture

Controller ↓ Service ↓ Repository ↓ JPA / Hibernate ↓ Database
residentRepository.findById(id);
residentRepository.save(resident);
🏢 Company Analogy
Manager → Accounts Department → Company Records. The manager doesn't directly go and manipulate the physical records; the accounts/data department handles them. Similarly: Service → Repository → Database.

Important point

When using Spring Data JPA, you commonly write an interface extending JpaRepository — you don't generally need to manually implement CRUD methods. Spring Data provides them.

Interview answer
"@Repository is used to indicate the persistence or data-access layer. It allows Spring to detect the repository component and provides database-related exception translation. In Spring Data JPA, repositories commonly extend JpaRepository."

4. @RestController

One of the most important annotations — used to create REST APIs.

@RestController
@RequestMapping("/api/residents")
public class ResidentController {
}

It is effectively a combination of @Controller + @ResponseBody. The important part is @ResponseBody — returned objects are generally written directly into the HTTP response body, commonly as JSON.

@GetMapping("/101")
public Resident getResident() {
    return new Resident(
        101,
        "Rahul",
        "A-101"
    );
}

Spring can convert the object into JSON:

{
  "id": 101,
  "name": "Rahul",
  "flatNumber": "A-101"
}
Real-life
React asks "Give me resident 101" → GET /api/residents/101. Spring Boot: @RestController → Find resident → Return object → JSON response.
Interview answer
"@RestController is used to create RESTful controllers in Spring Boot. It combines @Controller and @ResponseBody, so the return value of controller methods is written directly to the HTTP response, usually as JSON."

5. @Controller

Also a Spring MVC controller annotation, but with an important difference — traditionally used when the controller returns a view/page.

@Controller
public class HomeController {

    @GetMapping("/home")
    public String home() {
        return "home";
    }
}

Here "home" can represent a view such as home.html.

@Controller vs @RestController

@Controller ↓ Usually returns View @RestController ↓ Usually returns Data / JSON

Traditional Spring MVC:

@Controller
public class HomeController {

    @GetMapping("/home")
    public String home() {
        return "home";
    }
}

REST API:

@RestController
public class ResidentController {

    @GetMapping("/residents")
    public List<Resident> getResidents() {
        return residentService.getAllResidents();
    }
}

The second one returns data.

Interview answer
"@Controller is used in Spring MVC to define controller classes, especially when returning views. @RestController is designed for REST APIs and returns data directly in the HTTP response, commonly JSON."

6. @RequestMapping

Used to map an HTTP request to a controller or controller method.

@RestController
@RequestMapping("/api/residents")
public class ResidentController {}

This defines a common base URL: /api/residents. Then @GetMapping means GET /api/residents, and @GetMapping("/{id}") means GET /api/residents/{id}.

Why use @RequestMapping at class level?

Suppose you have @GetMapping("/api/residents"), @PostMapping("/api/residents"), @DeleteMapping("/api/residents/{id}") — repeating /api/residents everywhere is unnecessary. Instead, put @RequestMapping("/api/residents") at class level, then use @GetMapping, @PostMapping, @DeleteMapping("/{id}").

@RestController
@RequestMapping("/api/residents")
public class ResidentController {

    @GetMapping
    public List<Resident> getAll() {
        return residentService.getAll();
    }

    @PostMapping
    public Resident create(
            @RequestBody ResidentRequest request) {
        return residentService.create(request);
    }

    @DeleteMapping("/{id}")
    public void delete(
            @PathVariable Long id) {
        residentService.delete(id);
    }
}

The resulting APIs are:

GET /api/residents POST /api/residents DELETE /api/residents/101

7. HTTP Method Mappings

@GetMapping

Maps an HTTP GET request to a controller method.

@GetMapping
public List<Resident> getAllResidents() {
    return residentService.getAllResidents();
}

Request: GET /api/residents — Purpose: retrieve data.

@GetMapping("/{id}")
public Resident getResident(
        @PathVariable Long id) {
    return residentService.getResident(id);
}

Request: GET /api/residents/101 — Meaning: give me resident 101.

@PostMapping

Maps an HTTP POST request. Usually used to create a resource.

@PostMapping
public Resident createResident(
        @RequestBody ResidentRequest request) {
    return residentService.createResident(request);
}

Request: POST /api/residents, body: { "name": "Rahul", "flatNumber": "A-101" } — Meaning: create a new resident.

@PutMapping

Used for HTTP PUT requests. Generally used for complete updates/replacement.

@PutMapping("/{id}")
public Resident updateResident(
        @PathVariable Long id,
        @RequestBody ResidentRequest request) {
    return residentService.updateResident(id, request);
}

Request: PUT /api/residents/101

@PatchMapping

Used for HTTP PATCH requests. Generally used for partial updates.

@PatchMapping("/{id}")
public Resident updateMobile(
        @PathVariable Long id,
        @RequestBody Map<String, Object> data) {
    return residentService.partialUpdate(id, data);
}

Request: PATCH /api/residents/101, body: { "mobile": "9999999999" } — Meaning: change only the mobile number.

@DeleteMapping

Used for HTTP DELETE requests.

@DeleteMapping("/{id}")
public ResponseEntity<Void> deleteResident(
        @PathVariable Long id) {
    residentService.deleteResident(id);
    return ResponseEntity.noContent().build();
}

Request: DELETE /api/residents/101 — Meaning: delete resident 101.

8. @RequestBody

Extremely important — used to get data from the HTTP request body and convert it into a Java object.

Suppose React sends:

{
    "name": "Rahul",
    "flatNumber": "A-101",
    "mobile": "9876543210"
}

Controller:

@PostMapping
public Resident createResident(
        @RequestBody ResidentRequest request) {
    return residentService.createResident(request);
}

Spring converts JSON → ResidentRequest Java object. So request.getName() gives Rahul.

📝 Form Analogy
Imagine filling a form: Name: Rahul, Flat: A-101, Mobile: 9876543210. You submit the form — the server receives the information. In a REST API: Frontend → JSON Request Body → @RequestBody → Java Object.

9. @PathVariable

Suppose: GET /api/residents/101 — we want to extract 101.

@GetMapping("/{id}")
public Resident getResident(
        @PathVariable Long id) {
    return residentService.getResident(id);
}
URL: /api/residents/101 ↓ @PathVariable ↓ id = 101

10. @RequestParam

Used to read query parameters.

GET /api/residents?name=Rahul
@GetMapping
public List<Resident> search(
        @RequestParam String name) {
    return residentService.search(name);
}

Here name = Rahul.

Important Difference (Frequently Asked)

AnnotationData comes fromExample
@RequestBodyRequest body (JSON){ "name": "Rahul" }
@PathVariableURL path/residents/101
@RequestParamQuery parameter/residents?name=Rahul
@RequestBody ↓ JSON Body @PathVariable ↓ URL Path @RequestParam ↓ Query Parameter

11. Complete Controller Example

@RestController
@RequestMapping("/api/residents")
public class ResidentController {

    @GetMapping
    public List<Resident> getAllResidents() {
        return residentService.getAllResidents();
    }

    @GetMapping("/{id}")
    public Resident getResident(
            @PathVariable Long id) {
        return residentService.getResident(id);
    }

    @PostMapping
    public Resident createResident(
            @RequestBody ResidentRequest request) {
        return residentService.createResident(request);
    }

    @PutMapping("/{id}")
    public Resident updateResident(
            @PathVariable Long id,
            @RequestBody ResidentRequest request) {
        return residentService.updateResident(id, request);
    }

    @PatchMapping("/{id}")
    public Resident partialUpdate(
            @PathVariable Long id,
            @RequestBody Map<String, Object> data) {
        return residentService.partialUpdate(id, data);
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> deleteResident(
            @PathVariable Long id) {
        residentService.deleteResident(id);
        return ResponseEntity.noContent().build();
    }
}

Now your APIs become:

GET /api/residents GET /api/residents/101 POST /api/residents PUT /api/residents/101 PATCH /api/residents/101 DELETE /api/residents/101

13. Interview Q&A Bank Added

Q: Is @RequestParam required by default? What if the query param is missing?
Yes, @RequestParam is required by default — a missing param throws a 400 Bad Request. Use @RequestParam(required = false) or provide a defaultValue to make it optional.
Q: Can you have both @PathVariable and @RequestParam in the same method?
Yes — e.g. GET /api/residents/101/notices?type=urgent can combine @PathVariable Long id with @RequestParam String type in the same method signature.
Q: What does @RestController actually add beyond @Controller?
@RestController = @Controller + @ResponseBody. Without @ResponseBody, a @Controller method returning an object would be treated as a view name to resolve, not serialized data.
Q: Why use PATCH with Map<String, Object> instead of the full DTO?
Since PATCH only needs to update a subset of fields, using a generic Map lets the client send only the changed fields; the full DTO would force sending unrelated fields too, defeating the purpose of a partial update.
Q: What's the benefit of ResponseEntity over returning the object directly?
ResponseEntity gives control over the HTTP status code, headers, and body together — e.g. returning 204 No Content on delete versus always defaulting to 200 OK.
Q: Can @RequestMapping be used instead of @GetMapping/@PostMapping etc.?
Yes, via @RequestMapping(method = RequestMethod.GET) — but @GetMapping, @PostMapping etc. are shorthand, more readable, composed annotations introduced for convenience.

14. Memory Tricks Added

🧠 Layer Analogy Chain
Bank Counter (Controller) → Bank Officer (Service) → Company Records (Repository) — request flows down, decisions flow up.
🧠 Body vs Path vs Param
"Body is Big data (JSON), Path is the Position in the URL, Param is the Plus-sign after '?'."
🧠 @Controller vs @RestController
"@Controller shows you a page (View), @RestController hands you the data (JSON)" — think of View = visual, Rest = raw data.
🧠 Mapping to CRUD
GET = "fetch", POST = "make new", PUT = "replace whole", PATCH = "tweak one thing", DELETE = "remove" — same CRUD mnemonic as before, just annotated this time.

15. Common Bugs / Gotchas Added

⚠️ Forgetting @ResponseBody on a plain @Controller
If you use @Controller instead of @RestController but forget @ResponseBody, Spring tries to resolve the returned string as a view name, causing a "whitelabel error page" / view-not-found error instead of JSON output.
⚠️ Mismatched @PathVariable name and URL placeholder
If the URL has {residentId} but the method parameter is annotated @PathVariable Long id (no matching name specified), Spring throws a binding error — use @PathVariable("residentId") or keep names identical.
⚠️ Putting business logic inside the Controller
Beginners often write validation and business rules directly in controller methods. This breaks separation of concerns — that logic belongs in the @Service layer, keeping controllers thin (just handling HTTP concerns).
⚠️ Using @RequestParam when the value is part of the resource path
e.g. writing /api/residents?id=101 instead of /api/residents/101 for fetching a single resource. This is not idiomatic REST — path variables should represent resource identity, query params should represent filters/options.
⚠️ Repository not extending JpaRepository properly
Forgetting the generic types (<Entity, IdType>) or extending the wrong interface means Spring Data won't generate the expected CRUD methods, leading to compilation or runtime errors.
