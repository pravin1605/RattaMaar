1. Response Structure

📌 Proper Definition A response structure is a standardized format used by a REST API to send data, status information, and messages from the server to the client. It ensures that API responses follow a consistent structure across the application. 
{
    "success": true,
    "message": "Resident fetched successfully",
    "data": {
        "id": 101,
        "name": "Rahul",
        "flatNumber": "A-101"
    }
}

success → tells whether operation was successful. message → describes the result. data → contains actual response data.

Why do we need Response Structure?

Imagine your project has 50 APIs. Without a common structure, one API returns:

{
    "id": 101,
    "name": "Rahul"
}

Another API:

[
    {
        "id": 101
    }
]

Another:

{
    "error": "Resident not found"
}

The frontend has to understand different formats. With a common response structure — { "success": true, "message": "...", "data": {} } — the frontend always knows where to look.

📦 Courier Company Analogy
Every parcel has a standard label: Status / Message / Receiver / Package. Regardless of what's inside the parcel, the label follows the same format. Similarly, your API can have Success / Message / Data.

Project Example

public class ApiResponse<T> {

    private boolean success;
    private String message;
    private T data;
}

ApiResponse<ResidentResponse> can contain one resident. ApiResponse<List<ResidentResponse>> can contain multiple residents.

2. ResponseEntity

📌 Proper Definition ResponseEntity is a Spring class used to represent the complete HTTP response returned by a REST API. It allows us to control the response body, HTTP status code, and HTTP headers.

This is the important definition.

What can ResponseEntity control?

ResponseEntity │ ├── HTTP Status │ ├── Headers │ └── Body
return ResponseEntity.ok(response);

means: HTTP Status → 200 OK, Body → response.

Example

@GetMapping("/{id}")
public ResponseEntity<ApiResponse<ResidentResponse>> getResident(
        @PathVariable Long id) {

    ResidentResponse resident =
            residentService.getResident(id);

    ApiResponse<ResidentResponse> response =
            new ApiResponse<>(
                true,
                "Resident fetched successfully",
                resident
            );

    return ResponseEntity.ok(response);
}

Response:

HTTP/1.1 200 OK
{
    "success": true,
    "message": "Resident fetched successfully",
    "data": {
        "id": 101,
        "name": "Rahul"
    }
}

Common ResponseEntity methods

ok()

ResponseEntity.ok(response);

Returns: 200 OK

status()

ResponseEntity
    .status(HttpStatus.CREATED)
    .body(response);

Returns: 201 CREATED

noContent()

ResponseEntity.noContent().build();

Returns: 204 NO CONTENT

3. Response Structure vs ResponseEntity

This is very important for interviews.

Response StructureResponseEntity
Defines response body formatRepresents complete HTTP response
Usually custom classSpring-provided class
Contains fields like success, message, dataControls status, headers, body
Application-level designHTTP-level response handling
Remember
Response Structure = What data am I sending?  ·  ResponseEntity = How am I sending the HTTP response?

4. Custom Exception

📌 Proper Definition A custom exception is a user-defined exception created to represent a specific application or business error in a meaningful way.

Instead of using a generic:

throw new RuntimeException("Something went wrong");

we can create:

public class ResidentNotFoundException
        extends RuntimeException {

    public ResidentNotFoundException(String message) {
        super(message);
    }
}

Now we have a meaningful exception.

Why Custom Exceptions?

Suppose your SocietyHub application has: ResidentNotFoundException, SocietyNotFoundException, ComplaintNotFoundException, MaintenanceNotFoundException, DuplicateEmailException, FlatAlreadyOccupiedException. Each exception represents a specific problem. This makes the application: easier to understand, easier to debug, easier to maintain, easier to handle globally.

Example

Suppose we search for resident ID 999.

public ResidentResponse getResident(Long id) {

    Resident resident =
        residentRepository.findById(id)
            .orElseThrow(() ->
                new ResidentNotFoundException(
                    "Resident with ID "
                    + id
                    + " not found"
                )
            );

    return mapToResponse(resident);
}

If the resident doesn't exist, ResidentNotFoundException is thrown.

5. Global Exception Handler

A custom exception becomes much more useful when we handle it centrally.

📌 Proper Definition A global exception handler is a centralized mechanism in Spring Boot used to catch and handle exceptions thrown by controllers or service operations and convert them into appropriate HTTP responses.

We commonly use @RestControllerAdvice with @ExceptionHandler.

Example

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(
        ResidentNotFoundException.class
    )
    public ResponseEntity<ApiResponse<Void>>
    handleResidentNotFound(
            ResidentNotFoundException ex) {

        ApiResponse<Void> response =
            new ApiResponse<>(
                false,
                ex.getMessage(),
                null
            );

        return ResponseEntity
                .status(HttpStatus.NOT_FOUND)
                .body(response);
    }
}
Resident doesn't exist ↓ ResidentNotFoundException ↓ GlobalExceptionHandler ↓ HTTP 404 ↓ JSON Response

Response:

{
    "success": false,
    "message": "Resident with ID 999 not found",
    "data": null
}

6. Producer in RESTful Applications

📌 Proper Definition A producer in a RESTful application is an application or service that provides or exposes REST APIs for other applications or clients to consume.
Spring Boot ↓ Exposes REST APIs

Therefore Spring Boot is the producer for those APIs. Example: GET /api/residents, POST /api/residents, DELETE /api/residents/101 — Spring Boot provides these APIs.

7. Consumer in RESTful Applications

📌 Proper Definition A consumer in a RESTful application is an application or client that calls and uses REST APIs provided by another application or service.
React ↓ Calls Spring Boot API

React is the consumer of the Spring Boot APIs.

🍽️ Restaurant Analogy
Restaurant → Provides food → Producer. Customer → Consumes food → Consumer. Similarly: Spring Boot → Provides REST API → React → Uses REST API. Therefore: Spring Boot → Producer, React → Consumer.
⚠️ Important Point for Interview
Don't memorize "Frontend is always consumer" — that's not technically correct. Producer and consumer depend on which API communication you're talking about.

For example: SocietyHub → Payment Gateway. SocietyHub calls the Payment Gateway API. Therefore SocietyHub → Consumer, Payment Gateway → Producer. But the Payment Gateway could call another service: Payment Gateway → Notification Service. Then Payment Gateway → Consumer, Notification → Producer.

So the correct concept is:
The application providing an API is the producer, and the application calling that API is the consumer.

11. Interview Q&A Bank Added

Q: Why use @RestControllerAdvice instead of try-catch in every controller method?
try-catch in every method duplicates error-handling logic across the codebase. @RestControllerAdvice centralizes it in one place — cleaner, more maintainable, and guarantees consistent error response format across all controllers.
Q: What's the difference between @ControllerAdvice and @RestControllerAdvice?
@RestControllerAdvice = @ControllerAdvice + @ResponseBody, just like RestController vs Controller — it ensures exception handler return values are serialized directly as JSON rather than resolved as view names.
Q: How would you handle validation errors (e.g. @Valid failures) globally?
Add an @ExceptionHandler(MethodArgumentNotValidException.class) in the same GlobalExceptionHandler, extract field errors from the exception's BindingResult, and wrap them in the same ApiResponse structure with a 400 Bad Request status.
Q: Can one GlobalExceptionHandler catch a generic Exception.class as a fallback?
Yes — add an @ExceptionHandler(Exception.class) as a catch-all beneath more specific handlers, typically returning 500 Internal Server Error, so unexpected errors still return the standard response shape instead of a raw stack trace.
Q: Is a microservice always a producer or always a consumer?
Neither — the same service is often both: a producer for its own exposed APIs and a consumer when it calls other services (e.g. a payment gateway or notification service). The role is relative to each specific API call.
Q: What status code should a validation failure vs a not-found error return?
Validation failure (bad client input) → 400 Bad Request. Resource not found → 404 Not Found. Keeping these distinct helps consumers programmatically distinguish error types.

12. Memory Tricks Added

🧠 Structure vs Entity
"Structure is the Suitcase contents (what's packed inside: success/message/data), Entity is the whole shipment (status + headers + body)."
🧠 Producer/Consumer relativity
"Whoever answers the phone is the Producer; whoever dials is the Consumer" — and the same app can do both, just on different calls.
🧠 Exception flow
"Not Found → Named (custom exception) → Handled globally → Translated to HTTP" — NNHT: catchy shorthand for the whole error pipeline.
🧠 success/message/data
Think "SMD" like a courier label: Status, Message, Delivery(data) — same shape every time regardless of what's inside.

13. Common Bugs / Gotchas Added

⚠️ Returning raw entities/exceptions instead of the ApiResponse wrapper
If some endpoints return ApiResponse and others return raw objects or default Spring error pages, the frontend has to special-case each — defeating the entire purpose of a standardized response structure.
⚠️ Forgetting to register a new custom exception in the GlobalExceptionHandler
If you add FlatAlreadyOccupiedException but never add a matching @ExceptionHandler, it falls through to Spring's default error handling — producing an inconsistent, non-ApiResponse-shaped error body.
⚠️ Using the wrong HTTP status in exception handlers
Returning 200 OK with "success": false in the body (instead of an appropriate 4xx/5xx status) breaks HTTP semantics and can confuse consumers or monitoring tools that check status codes rather than body content.
⚠️ Overly broad exception hierarchies
Catching generic RuntimeException everywhere instead of specific custom exceptions loses the meaningful, debuggable error information that custom exceptions were designed to provide.
⚠️ Leaking internal exception messages/stack traces to the client
For unexpected 500-level errors, avoid putting raw exception messages or stack traces in the response body — return a generic safe message instead and log the details server-side.
