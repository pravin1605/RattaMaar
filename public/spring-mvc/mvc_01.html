What is Spring MVC? overview

  • Used to develop web applications.
  • A sub-framework of Spring used to build web apps.
  • Built on top of the Servlet API.
  • Follows the Model–View–Controller design pattern.
  • Implements core Spring features like IoC and Dependency Injection.
  • Internally uses the Servlet API.

Why use it?

  • Separates responsibilities — Model, View, Controller each own one job.
  • Powerful, flexible configuration (XML or Java-based).
  • Inherits Spring core features like IoC out of the box.
  • Supports rapid application development.
  • Flexible, easy to test, feature-rich.

MVC Architecture design pattern

A way of organizing application code into three distinct roles.

Model

Data + business logic — Java objects, services, DAO layer.

View

The UI — JSP, Thymeleaf, HTML, etc.

Controller

Handles user requests, processes input, talks to the Model, returns a View.
Without MVC: UI, business logic, and database code are all mixed together in one Servlet/JSP — fine at small scale, unmanageable as the app grows.

The Hotel Analogy intuition

A mental model for why separating roles matters.

Without MVC — the lone owner

One person takes the order, cooks, serves, collects money, and cleans. If a new customer arrives while he's in the kitchen, they wait. Result: confusion, delay, poor service — exactly what happens when Servlets/JSP handle everything in one place.

With MVC — a structured hotel

RoleMVC partJob
WaiterControllerTakes the order, passes it on, brings back the result — doesn't cook.
ChefModelPrepares the food (business logic) behind the scenes.
Dining tableViewDisplays the final result — customer never sees the kitchen.
  1. Customer tells the Waiter (Controller): "I want Chicken Biryani."
  2. Waiter passes the order to the Chef (Model).
  3. Chef prepares the food.
  4. Chef hands the dish back to the Waiter.
  5. Waiter serves it on the Table (View) to the customer.

How a Request Flows request lifecycle

Client request→ DispatcherServlet→ Handler Mapping→ Controller→ Model / Service / DAO
View name + Model→ View Resolver→ View (JSP/HTML)→ Response to client
  1. 1Client sends a request, e.g. /hello.
  2. 2DispatcherServlet (the Front Controller) receives every request first.
  3. 3Handler Mapping decides which Controller should handle it.
  4. 4The @Controller method runs — processes the request, calls Service/DAO if needed.
  5. 5The Model returns processed data (Employee, Product, Order, etc.).
  6. 6Controller returns a logical view name + data back to the DispatcherServlet.
  7. 7View Resolver maps the logical name to an actual file — e.g. "hello" → hello.jsp.
  8. 8The View renders the UI using the model data.
  9. 9DispatcherServlet sends the final response to the client.

Project Setup XML-based config

Create a Maven project and add the Spring MVC dependency.

Note: check your server version — Tomcat 9 or below needs javax packages; newer Tomcat needs jakarta packages instead.

    <version>5.2.4.RELEASE</version>

The Controller @Controller & @RequestMapping

@Controller

Marks a class as a Spring MVC Controller. Handles user requests, talks to the Model, returns a View. Also enables auto-scanning of the class.

@RequestMapping

Maps an HTTP request to a handler method — "when a request hits this URL, run this method." Works at class level and method level.

Key points

  • A Controller processes requests using the Service/DAO layer.
  • @RequestMapping("/demoFile") on a method → runs on requests to /demoFile.
  • Restrict method/verb: @RequestMapping(path="/home", method=RequestMethod.POST).
  • Return type is always String (a view name) or ModelAndView.
@RequestMapping("/add")
public String add() {
    int a = 10 + 20;
    return "output.jsp";
}

AnnotationEquivalent to
@GetMapping@RequestMapping(method = RequestMethod.GET)
@PostMapping@RequestMapping(method = RequestMethod.POST)

@DeleteMapping@RequestMapping(method = RequestMethod.DELETE)

Controller → View sending data out

Two approaches: the Model interface, or the ModelAndView class.

a) Model interface — data only

Use addAttribute(key, value) to pass key–value pairs to the view.

@RequestMapping("/sample")
public String showRegisterFile(Model model) {
    model.addAttribute("name", "Rani");
    model.addAttribute("percentage", 78);
    return "Demo.jsp";
}

b) ModelAndView — data + view together

  • setViewName("file") — with extension = complete response; without = incomplete response.
  • addObject(key, value) — attach data.
Access in JSP: call getAttribute("key") in scriptlets.
@ResponseBody: prints data/JSON directly to the browser.
Redirect: return "redirect:urlOfMethod"; — pass data along with RedirectAttributes.addFlashAttribute().
Session storage: @SessionAttributes on the controller + Model/ModelAndView to store, HttpSession.getAttribute() to read elsewhere.

View → Controller receiving user input

  1. Create a form with input fields, each identified by a name attribute.
  2. Read that data in the controller using one of three approaches.

@RequestParam — one annotation per field

Reads a value from an input box or a URL query parameter.

@RequestMapping("/add")
public ModelAndView add(@RequestParam("first") int num1,
                         @RequestParam("second") int num2) {
    int result = num1 + num2;
    ModelAndView mv = new ModelAndView();
    mv.setViewName("output.jsp");
    mv.addObject("op", result);
    return mv;
}

@PathVariable — data embedded in the URL

// localhost:8080/add/10/20
@RequestMapping("/add/{n1}/{n2}")
public ModelAndView add(@PathVariable("n1") int num1,
                         @PathVariable("n2") int num2) {
    int result = num1 + num2;
    ModelAndView mv = new ModelAndView();
    mv.setViewName("output.jsp");
    mv.addObject("op", result);
    return mv;
}

@ModelAttribute — bind a whole object

Create a class matching the form's fields; input box names must match the class's variable names.

public class Addition {
    private int num1;
    private int num2;
    // getters and setters
}

Spring fetches each field by name, sets it via the setter, and hands the populated object to the controller:

@RequestMapping("/add")
public ModelAndView add(@ModelAttribute Addition info) {
    int result = info.getNum1() + info.getNum2();
    ModelAndView mv = new ModelAndView();
    mv.setViewName("output");
    mv.addObject("op", result);
    return mv;
}

@ModelAttribute at method level

Runs before every request-handling method in the controller — useful for data common to all views (e.g. page header, footer text).

@ModelAttribute
public void common(Model m) {
    m.addAttribute("Header", "Learn code with Shubh");
    m.addAttribute("Dec", "Home for Programmer");
}

Java-based Configuration alternative to XML

  1. 1Create a Config class with @Configuration + @ComponentScan(basePackages="package name").
  2. 2Create a WebInitializer extending AbstractAnnotationConfigDispatcherServletInitializer.
  3. 3Create a Controller.
  4. 4Create a View to render.

1 · Config class

@Configuration
@ComponentScan(basePackages = "package name")
public class Config {
    // helper @Bean methods go here, if needed
}

2 · WebInitializer

public class WebInitializer extends AbstractAnnotationConfigDispatcherServletInitializer {

    @Override
    protected Class<?>[] getRootConfigClasses() {
        return null;
    }

    @Override
    protected Class<?>[] getServletConfigClasses() {
        return new Class[] { Config.class };
    }

    @Override
    protected String[] getServletMappings() {
        return new String[] { "/" };
    }
}

Form Validation bean validation (JSR-380)

Spring MVC integrates with the standard javax.validation / jakarta.validation API to validate bound objects automatically.

Add dependency

<dependency>
    <groupId>org.hibernate.validator</groupId>
    <artifactId>hibernate-validator</artifactId>
    <version>6.1.5.Final</version>
</dependency>

Annotate the model

public class Addition {
    @NotNull(message = "First number is required")
    private Integer num1;

    @Min(value = 1, message = "Second number must be positive")
    private Integer num2;
    // getters and setters
}

Validate in the controller

@RequestMapping("/add")
public String add(@Valid @ModelAttribute Addition info,
                   BindingResult result) {
    if (result.hasErrors()) {
        return "form.jsp";   // re-show form with errors
    }
    // proceed
    return "output.jsp";
}
Note: BindingResult must come immediately after the @Valid argument, or Spring throws an exception instead of populating errors.

Interceptors pre/post-process requests

Similar to filters, but Spring-aware — run logic before/after a controller executes (e.g. logging, auth checks, locale switching).

1 · Implement HandlerInterceptor

public class LoggingInterceptor implements HandlerInterceptor {

    public boolean preHandle(HttpServletRequest req,
                              HttpServletResponse res,
                              Object handler) {
        System.out.println("Request URL: " + req.getRequestURI());
        return true;   // false = stop the chain here
    }

    public void postHandle(HttpServletRequest req,
                            HttpServletResponse res,
                            Object handler,
                            ModelAndView mv) {
        System.out.println("Controller finished, view not yet rendered");
    }

    public void afterCompletion(HttpServletRequest req,
                                 HttpServletResponse res,
                                 Object handler,
                                 Exception ex) {
        System.out.println("Response fully sent");
    }
}

2 · Register it

@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new LoggingInterceptor())
                .addPathPatterns("/**")
                .excludePathPatterns("/login", "/css/**");
    }
}

Exception Handling @ExceptionHandler & @ControllerAdvice

Local — inside one controller

@Controller
public class UserController {

    @RequestMapping("/user/{id}")
    public String getUser(@PathVariable int id, Model model) {
        if (id <= 0) throw new IllegalArgumentException("Invalid id");
        // ...
        return "user.jsp";
    }

    @ExceptionHandler(IllegalArgumentException.class)
    public String handleBadId(IllegalArgumentException ex, Model model) {
        model.addAttribute("error", ex.getMessage());
        return "error.jsp";
    }
}

Global — across all controllers

@ControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(Exception.class)
    public ModelAndView handleAll(Exception ex) {
        ModelAndView mv = new ModelAndView("error");
        mv.addObject("message", ex.getMessage());
        return mv;
    }
}
@ControllerAdvice centralizes error handling for the whole application instead of repeating @ExceptionHandler in every controller.

REST Controllers @RestController & JSON

For APIs that return data (typically JSON) instead of a rendered view.

@RestController

Equivalent to @Controller + @ResponseBody on every method — the return value is written straight to the response body, not resolved to a view.

@RequestBody

Binds the incoming JSON request body directly to a Java object. 
@RestController
@RequestMapping("/api/users")
public class UserApiController {

    @GetMapping("/{id}")
    public User getUser(@PathVariable int id) {
        return userService.findById(id);   // serialized to JSON automatically
    }

    @PostMapping
    public User createUser(@RequestBody User user) {
        return userService.save(user);
    }
}
Needs the Jackson library on the classpath (jackson-databind) for automatic Java ⇄ JSON conversion.

Quick Recap interview-style Q&A

Q: What is the DispatcherServlet?
A: The Front Controller of Spring MVC — every incoming request passes through it first, and it delegates to the right controller.
Q: Difference between @RequestParam and @PathVariable?
A: @RequestParam reads query-string/form parameters (?key=value); @PathVariable reads values embedded directly in the URL path (/add/10/20).
Q: Model vs ModelAndView?
A: Model only carries data to the view (the method still returns the view name as a String). ModelAndView carries both the data and the view name in one object.
Q: What does the View Resolver do?
A: Converts a logical view name returned by the controller (e.g. "hello") into an actual resource path (e.g. /WEB-INF/views/hello.jsp).
Q: @Controller vs @RestController?
A: @Controller returns view names to be resolved into pages. @RestController returns data (usually JSON) written directly to the response body.
Q: How do interceptors differ from filters?
A: Filters are part of the raw Servlet API and run outside Spring's context; interceptors are Spring-aware and can access handler details like the controller method being invoked.
